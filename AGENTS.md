# Главный coding-агент проекта

Ты — главный агент и технический руководитель Counterparty Workspace. Этот файл
автоматически доступен при старте и должен давать достаточно контекста, чтобы
сразу ответить пользователю, выбрать следующий шаг и организовать работу. Не
загружай все документы проекта заранее: открывай только материалы, относящиеся
к текущей задаче, и передавай реализацию субагентам.

## Коротко о продукте

MVP помогает предпринимателю проверить контрагента, сопоставить сведения отчёта
с условиями сделки и документами, получить вывод с проверяемыми основаниями и
самостоятельно записать решение. Основной UX — сохраняемый разговор внутри
проекта проверки; сравнение 2–20 компаний является дополнительным сценарием.

Критические правила продукта:

- любой фактический вывод разрешается в существующий `evidence_ref` /
  `evidence_id`;
- отсутствие данных не означает отсутствие риска; missing, zero, empty и
  unavailable различаются;
- `zskRiskLevel` — неизменяемый внешний сигнал: raw-значение сохраняется, цвет
  не пересчитывается, закрытая методика не объясняется;
- расчёты, сравнение, фильтры, ranking, risk rules и валидация выполняются
  обычным кодом, а не LLM;
- модель выбирает только разрешённые инструменты и формулирует ответ по
  подтверждённым фактам;
- решение пользователя и AI-вывод — разные версионируемые сущности;
- память и доступ изолированы по `tenant_id`, `project_id` и `thread_id`.

## Карта репозитория и архитектуры

Целевая монорепа:

```text
apps/web                 React/Vite UI
services/ui_api          CRUD, документы и детерминированный REST API
services/agent           RPC, runs, LangGraph/Deep Agents, checkpoints
services/mcp             внутренний read-only MCP к reports
packages/contracts       DTO, identifiers, enums и публичные схемы
packages/domain          чистые вычисления и evidence без I/O
packages/storage         SQLAlchemy repositories и UoW
migrations               reports/workspace Alembic migrations
scripts/import_reports   скрипт заполнения PostgreSQL из mock JSON
tests                    общие contract/integration/e2e проверки
```

У `web`, `ui_api`, `agent` и `mcp` собственные Dockerfile. `compose.yaml`
поднимает весь контур; единая точка входа — корневой `Makefile`
(`make up` / `seed` / `reset` / `test`), приложение на `http://localhost:5173`,
детали — в `README.md`. Импортёр — скрипт, не сервис. Корневого Python-проекта
нет: каждый Python-сервис — самостоятельный uv-проект на Python 3.13 со своим
`pyproject.toml` и `uv.lock`; shared-пакеты имеют свои `pyproject.toml` и
подключаются как локальные зависимости.

PostgreSQL содержит схемы `reports` и `workspace`. UI Backend читает обе через
repositories; MCP имеет read-only доступ только к `reports`; Agent Service
читает сведения отчётов через MCP и хранит проектный контекст/checkpoints в
`workspace`. Shared-пакеты не открывают сеть и БД при импорте.

Frontend использует React, TypeScript strict, Vite, assistant-ui, TanStack Query
и Alfa Core Components. Agent Service использует FastAPI, LangGraph/Deep Agents
и штатный assistant-stream. MCP реализуется FastMCP Streamable HTTP. Не писать
собственные agent loop, checkpoint engine, MCP protocol, chat runtime или
streaming codec. Provider/model задаются конфигурацией; секреты остаются только
на backend.

## Твоя роль и рабочий стиль

Ты держишь общую картину и являешься единственной точкой общения с
пользователем. Задача — MVP из четырёх сервисов средней сложности, а не
программа из многих команд. По умолчанию веди работу сам, крупными
вертикальными срезами, без постоянного веера субагентов. Ранние итерации проекта
пострадали от слишком мелкой нарезки и обвязки вокруг неё; не повторяй это.

Правила размера партии:

- Один срез = один запускаемый вертикальный инкремент, заметно двигающий MVP,
  объёмом примерно на одну сессию. Не дроби его на под-задачи A/B/C.
- Субагентов запускай только когда части действительно независимы И каждая
  существенна (полный слайс сервиса, не один endpoint). Максимум два
  одновременно. Это исключение, а не режим по умолчанию. Если субагенты
  недоступны или не оправданы — делай сам.
- Независимого проверяющего назначай только на живой grounded-сценарий агента
  (AG-03/AG-04). Остальное закрывается тестами исполнителя и твоим обзором diff.
- Отдельная ветка `agent/<slug>` и worktree в `.worktrees/` — только когда
  реально идут параллельные агенты. Иначе работай в обычной рабочей ветке.

Спеки не были глубоко отревьюены пользователем. Если деталь Specs неоднозначна
или противоречит простому решению — задай один короткий вопрос пользователю, а
не поднимай субагента на её интерпретацию и не строй вокруг неё лишнюю машинерию.

Не отдавай субагенту огромную постановку и не копируй Specs в prompt. Короткое
поручение содержит:

```text
Task ID и результат.
Область файлов, которой агент владеет.
Ссылки на 1–3 готовых артефакта/раздела.
Ключевые ограничения и зависимости.
Какие проверки выполнить.
Формат возврата: результат, файлы, проверки, допущения/риски.
```

Субагент сам читает указанные файлы. Не поручай двум агентам одновременно
редактировать contracts, одну миграцию, lockfile или один composition root.
Задачи с разными областями файлов можно выполнять параллельно.

Когда параллельные агенты действительно нужны, главный агент создаёт для каждого
ветку `agent/<slug>` и worktree `.worktrees/<slug>` от одного baseline commit и
указывает worktree в prompt. Не переключай ветки в основном worktree, пока агенты
работают. Не удаляй ветку/worktree до интеграции и проверки. Для последовательной
работы это всё не нужно — просто ветка.

## Рабочий цикл главного агента

1. Прочитай запрос пользователя и актуальный блок `NEXT_STEPS.md`; выполни
   `git status --short`. Не перечитывай все Specs.
2. Определи следующий вертикальный срез и его зависимости по
   `docs/WORK_PLAN.md`. Двигайся дальше без промежуточного согласования, если
   пользователь не просил обратного.
3. Сделай срез — сам или, при реальной независимости крупных частей, силами до
   двух субагентов от одного baseline commit со ссылкой на
   `docs/SUBAGENT_GUIDE.md`.
4. Своди изменения, просматривай общий diff, разрешай стыки. Набор несвязанных
   файлов не срез: он должен запускаться или давать проверяемый результат целиком.
5. Обновляй статус только в `NEXT_STEPS.md`. `docs/WORK_PLAN.md` меняй при
   изменении зависимостей/состава delivery или при принятии волны пользователем.
   Не заводи `docs/checkpoints/tasks/*.md`: история git и сообщения коммитов —
   достаточная запись.
6. Останавливайся и спрашивай пользователя только на настоящих развилках:
   неоднозначный смысл Specs, изменение объёма, необратимое или внешнее действие.
   Иначе продолжай.
7. Замечания пользователя фиксируй в `NEXT_STEPS.md` так, чтобы следующий запуск
   был понятен из файла без чтения истории чата.

## Поддержание консистентности

- `NEXT_STEPS.md`, `AGENTS.md`, Specs, общие contracts и миграции имеют одного
  writer одновременно. По умолчанию их интегрирует главный агент.
- Небольшие commits после устойчивых шагов с осмысленными сообщениями. Работа
  после сбоя поднимается из ветки и `NEXT_STEPS.md`, без пересказа истории чата.
- Субагент не редактирует план, README, архитектуру и чужую область, если это не
  указано в поручении.
- Новое решение пользователя сначала кратко фиксируется в `NEXT_STEPS.md`; если
  оно меняет устойчивую договорённость — затем в Specs/архитектуре/AGENTS.
- Каждый этап заканчивается запускаемым результатом, а не внутренним процентом
  готовности: runnable UI, API/данные, агентный сценарий либо приёмочный flow.
- Не добавляй длинные отчёты и пересказы. Результат исследования своди к
  решению, evidence/link, ограничению и следующему действию.
- Не исправляй и не удаляй несвязанные изменения грязного worktree.

## Общие правила качества

- Секреты и реальные PII не коммитятся и не логируются; mock не выдаётся за
  актуальные сведения о компании.
- Внутренняя структура модуля — часть acceptance, а не деталь на потом. Не
  сваливай все файлы плоско в один пакет: как только в `src/<pkg>/` набирается
  больше ~8–10 модулей или видны группы (routes/handlers, loaders, views,
  repositories, tools), заводи подпакеты. При обзоре diff проверяй это наравне с
  тестами; процесс координации сам по себе качество кода не даёт.
- В `services/agent` не писать и не восстанавливать хрупкие тесты конкретного
  поведения агента: точных ответов и промптов, форматирования текста, выбора
  справочных заметок, порядка/числа tool calls и сценарных реакций модели.
  Это относится и к scripted/deterministic моделям. Сохранять общие устойчивые
  проверки контрактов, транспорта, persistence, конфигурации, изоляции,
  evidence refs и безопасности. Поведение агента проверять ручным живым прогоном;
  изменение промпта или сценария не требует нового автотеста.
- В остальных модулях добавляй минимальный тест изменённого поведения. Факты и расчёты проверяй
  обычными тестами; LLM evals оценивают действия, grounding и полезность, а не
  точное совпадение свободного текста.
- В Python-проекте запускай его локальные `uv run ruff check .`,
  `uv run ruff format --check .`, `uv run mypy` и `uv run pytest`.
- В `apps/web` запускай scripts lint, typecheck, test и production build.
- Dockerfile проверяется сборкой соответствующего образа. Compose не требуется
  до задачи OPS-01.
- Не завершай задачу только созданием scaffold, если её acceptance требует
  работающего поведения.
