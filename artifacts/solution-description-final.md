# Counterparty Workspace — проверка контрагентов для Альфа-Бизнеса

## Общее описание (аннотация)

Мы сделали рабочее пространство для проверки контрагентов перед сделкой. В нём предприниматель может изучить отчёт о компании, задать вопросы ИИ-помощнику и сохранить своё решение.

Отчёт даёт сведения, но их ещё нужно применить к своей ситуации. Например, понять, что проверить перед авансом поставщику или отсрочкой платежа покупателю. При нескольких кандидатах приходится сравнивать показатели из разных отчётов.

Работа начинается с проекта проверки. Пользователь добавляет компанию, описывает задачу и обсуждает её с помощником. История сохраняется, поэтому к проверке можно вернуться позже. Для выбора среди кандидатов есть таблица сравнения 2–20 компаний.

Помощник читает доступные разделы отчёта и даёт ответ со ссылками на конкретные сведения. Пользователь может открыть источник, проверить цифры и уточнить вопрос. Пробелы в данных остаются видимыми, банковская оценка не пересчитывается.

Интерфейс написан на React. Серверная часть отвечает за проекты и отчёты, агентный сервис — за диалог, внутренний MCP — за чтение данных агентом. Отчёты и история хранятся в PostgreSQL. Расчёты выполняет код, работу модели с инструментами организует LangGraph.

Агент работает на 100 демонстрационных отчётах из кейса. Реализованы проекты, отчёт компании, сравнение, диалог с моделью, открытие источников и запись решения пользователя. Проверены отдельные сценарии с реальной моделью и сохранение истории.

Дальше планируем ускорить ответы, добавить документы сделки и провести пользовательский пилот. Он покажет, сколько времени экономит помощник и какие ошибки остаются. Пока такой замер не проведён.

## Проблематика

При проверке контрагента предпринимателю нужно ответить на практический вопрос: можно ли переходить к сделке и что перед этим уточнить. Для этого он читает отчёт, сопоставляет цифры, ищет существенные для своей задачи сведения и записывает выводы.

Эта работа усложняется, когда компаний несколько или меняются условия оплаты. Часть данных может отсутствовать, показатели — относиться к разным периодам. Банковский светофор не заменяет разбор финансов, а отсутствие сведений о риске не доказывает его отсутствие. В отдельных отчётах и заметках также теряется история: что уже проверяли и почему приняли решение.

## Постановка задачи

Собрать в одном проекте данные о контрагенте, обсуждение сделки и решение пользователя. Для этого нужны:

- поиск и добавление компаний в проверку;
- отчёт и сравнение по одинаковым показателям и периодам;
- диалог с учётом вопроса и уточнений пользователя;
- переход от ответа к источнику;
- сохранение истории, обоснования и условий решения.

Помощник должен объяснять доступные факты и указывать, чего не хватает. Выбор контрагента и решение о сотрудничестве остаются за человеком.

## Описание технического решения

Приложение состоит из четырёх частей:

| Компонент | За что отвечает | Технологии |
|---|---|---|
| Web | Проекты, чат, отчёт, сравнение и решение | React, TypeScript, Vite, assistant-ui, Alfa Core Components |
| UI Backend | API проектов, отчётов, сравнений и решений | FastAPI, SQLAlchemy |
| Agent Service | Диалог, вызов инструментов и память | Deep Agents, LangGraph, LangChain, assistant-stream |
| Внутренний MCP | Чтение отчётов агентом | FastMCP, Streamable HTTP |

В PostgreSQL отчёты хранятся в схеме `reports`, проекты и разговоры — в `workspace`. Скрипт импорта загружает исходный JSON, сохраняя даты и происхождение значений. Повторный импорт не создаёт дубликаты. Весь контур запускается через Docker Compose.

Агент получает вопрос и читает нужные разделы через MCP. Каждый фактический вывод должен ссылаться на существующий `evidence_ref`. Перед показом проверяются ссылки и доступность оснований; неподтверждённые фрагменты исправляются или исключаются. Пользователь открывает источник прямо из ответа.

Расчёты и сравнение выполняются общим кодом для API и MCP. Модель не меняет банковские индикаторы, включая `zskRiskLevel`, и не объясняет закрытую методику оценки. Ноль, отсутствующее значение, пустой раздел и недоступные данные обрабатываются раздельно.

Доступ и память разделены по организации, проекту и разговору. MCP имеет доступ к отчётам только на чтение; ключи модели остаются на сервере. Завершённая история сохраняется в PostgreSQL и восстанавливается после перезагрузки страницы. Решение пользователя записывается отдельно, вместе с обоснованием и условиями; прежние записи сохраняются.

## Полученные результаты

Собран локально запускаемый агент. В нём работают:

- импорт 100 демонстрационных отчётов;
- создание проектов и добавление компаний;
- просмотр профиля, статуса, финансовых показателей и банковских сигналов;
- сравнение 2–20 компаний с открытием источников;
- диалог с реальной моделью через внутренний MCP;
- сохранение завершённого разговора и решения пользователя.

В ходе разработки проверялись расчёты, импорт, контракты API, доступ к данным и интерфейс. Проведены ручные прогоны с моделью: проверка поставщика перед авансом, сравнение трёх кандидатов и обсуждение компании с высокими внешними сигналами риска. Проверены восстановление истории и отображение интерфейса на разных размерах экрана.

Агент использует данные кейса, а не актуальные сведения о компаниях. Не все разделы отчётов заполнены. Работа с документами, отдельный автоматически создаваемый ИИ-вывод и внешний MCP ещё не готовы. Скорость и устойчивость диалога требуют доработки; экономия времени и влияние на удержание клиентов пока не измерены.

## Дальнейшие планы по развитию

1. **Ускорить и проверить диалог.** Сократить задержки, улучшить восстановление после сбоев и проверить ответы на большем наборе реальных задач.
2. **Провести пилот.** Сравнить проверку по отчётам, в таблице без ИИ и с агентом. Измерять время, ошибки и долю завершённых задач. Цель — снизить медианное время минимум на 30% без ухудшения качества.
3. **Добавить документы.** Загружать PDF, DOCX и XLSX, сопоставлять условия договора с отчётом и давать ссылки на фрагменты файлов.
4. **Развить итог проверки.** Сохранять версии ИИ-вывода и показывать, что изменилось после уточнения условий сделки.
5. **Подготовить интеграцию с банком.** Подключить актуальные источники, согласовать доступ, хранение и аудит. Отдельно проработать внешний MCP для привычных ИИ-клиентов пользователя.
