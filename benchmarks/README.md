# Проверка механизмов и качества ответов

## Автоматические регрессии без сети

Генератор `synthetic.py` строит 100 явно синтетических ЮЛ и независимый Truth:
валидные ИНН/ОГРН, знак прибыли, пропуски, разные годы, банковский сигнал и числа
больше безопасного диапазона JavaScript Number. Seed фиксирован, меньшие наборы
совпадают с префиксом большого. Рабочие данные приложения не заменяются.

## Воспроизведение

```bash
uv run pytest tests/test_synthetic_benchmark.py tests/test_projects.py tests/test_project_dialogue.py -o addopts='' --tb=short
```

Сетевых запросов к LLM в этих тестах нет. Provider-транспорт подменён управляемым
ответом, но поиск, расчёты, граф, API, SQLite и парсеры выполняются настоящие.

## Что проверяется

- Независимые ожидаемые ID и точные Decimal-значения для всех 100 компаний.
- Матрицы 2/11/20/50/100: порядок, все участники, пропуски, год и собственные evidence.
- Ответ для 20/50/100 компаний: контекст до 30 000 символов и полный состав ответа.
- Неверные ID, лишняя проза и допустимый ID неправильной явно названной темы.
- Checkpoint без реквизитов/отчётов, изоляция сессий, фокус на компании №100.
- Отбор 5 → 3, документ, план, diff, принятие и отказ при повторном принятии.
- Чужой владелец, старая ревизия, смена источника/состава/цели и восстановление проекта.
- Обычный вопрос при длинном документе, отдельные цитаты, квартал/неподдержанный год,
  неправильный явный контрагент и единое время доказательств в HTTP-ответе.
- После успешного вопроса предложение резюме всё ещё можно явно принять.

Полный прогон 04.09.2026: **296 Python-тестов, 15,05 с, все прошли**.
Frontend: **7 тестов**, сборка TypeScript/Vite успешна. Есть предупреждение
зависимости Starlette об устаревающем alias AnyIO, без падений.

В браузере проверен реальный локальный источник: сравнение трёх компаний,
отбор двух, сохранение проекта, AI-план, загрузка синтетического предложения,
связь с вопросом, diff и принятие memo. Живой LLM ответил про убытки группы
и условия из документа. Проверены источники, восстановление после reload,
фильтры и размеры 1440×960 / 390×844. Это smoke-проверка, не экспертный eval.
Отдельный тест принудительно превышает лимит RSS парсера и проверяет завершение
дочернего процесса; DOCX с внешней XML-сущностью отклоняется.

## Чего результаты не доказывают

Это не оценка качества реальной модели и не нагрузочный тест. В синтетическом
наборе нет ИП, сложных судебных/исполнительных коллекций, неоднозначных имён и
полной многолетней финансовой матрицы; часть этих случаев покрыта отдельными
регрессиями на выданном JSON. Не проверены все перефразирования вопросов,
сложные макеты PDF, OCR, исчерпывающее понимание договоров и юридические выводы.

Следующий этап — независимые экспертные вопросы, разметка ожидаемых тем/источников,
реальный LLM-прогон и пользовательское сравнение «PDF против workspace».

## Живой аналитический сценарий

`evaluate_review.py` запускается только с явным `--live`, так как использует ключ
и тариф текущего подключения. Источник — реальные отчёты настроенного JSON;
SQLite для каждого прогона временная. Рабочие сессии и источник не изменяются.

```bash
uv run python -m benchmarks.evaluate_review --live --trace \
  --inn 1684017097 --inn 9705152496 --inn 9714079997 \
  --output /tmp/counterparty-eval.json
```

Проверяются выбор группы, задача поставки с авансом, переход к постоплате,
фокус на второй компании, пробелы, совместный анализ документа и отчётов,
расхождение документа с текущими условиями. Сумма, срок и неподписанный проект
условий — явно демонстрационный ввод пользователя, не подмена исходных отчётов.
Флаг `--suite core` исключает документный сценарий; `--suite project` оставляет
подготовку группы/условий и два вопроса с документом.

JSON содержит длительности, статусы, проверку существования источников и текст
ответа для ручной оценки. `evidence_valid` проверяет ссылки, **не истинность смысла**.
Отдельно проверяйте: отвечает ли текст задаче, верны ли компания/период/единицы,
не превращён ли ноль в пропуск, удержаны ли текущие условия, обозначены ли
неизвестное и полезный следующий шаг. Не коммитьте локальные результаты с данными.

## Понятность и польза ответа

`evaluate_quality.py` проверяет диалоги на реальных отчётах: подрядчик с авансом,
уточнение работ/суммы/срока, переход на постоплату и вопрос об опыте; затем сравнение
трёх компаний, фокус на второй и возврат к пробелам группы.

```bash
PYTHONPATH=src:. uv run python -m benchmarks.evaluate_quality --live \
  --output /tmp/counterparty-quality.json
```

`--dialogue contractor` или `--dialogue group` ограничивает прогон одним диалогом.
`--dialogue feedback` повторяет обратную связь пользователя: подрядчик с авансом →
достаточность зелёного статуса → независимый покупатель с оплатой через 60 дней →
смена отсрочки на 30 дней и указание суммы. Проверяем, что нет отказа поиска,
старый аванс не переносится на новую компанию, роль продавца-пользователя не заменяет
роль покупателя-контрагента, а текст отвечает про получение оплаты, не приёмку работ.
В результате есть текст, число слов, время, источники и признак полной резервной сводки.
`used_fallback` означает совпадение итогового текста с полной резервной сводкой;
`fallback_considered` — только то, что такая версия создавалась, но могла быть отклонена.
Также сохраняются число попыток генерации и обезличенные причины отклонения черновиков:
это позволяет отличить смысловую ошибку от неподтверждённого числа, не записывая запрос
к провайдеру или исходный отчёт.
Отсутствие этого признака не исключает замену одного отклонённого абзаца. Автоматического
балла полезности нет: вручную сверяем роли в судах, годы/пропуски, текущую оплату,
относимость действий и понятность языка. Зелёный HTTP-статус не заменяет эту проверку.

## Сценарии из пользовательского файла

Набор `--dialogue cases` — шесть диалогов, 15 сообщений: аванс подрядчику,
отсрочка покупателю и смена 60 → 30 дней, частичные суммы взысканий, спокойная
проверка, отсутствие финансов и сравнение с переходом ко второму участнику и обратно.
Основа — присланный пользователем LLM-файл версии 2, **не эталон ответов**.
Числа и источники сверяются с подключённым JSON: судебные сводки двух компаний
не совпали с ожидаемыми значениями файла. Рабочие данные не заменяются.

```bash
PYTHONPATH=src:. uv run python -m benchmarks.evaluate_quality --live \
  --dialogue cases --output /tmp/counterparty-cases.json
```

Для короткого повтора доступны `case_advance`, `case_buyer`, `case_enforcement`,
`case_calm`, `case_missing` и `case_group`. Время включает роутер, аналитический цикл,
проверку и исправления. Каждый диалог получает отдельную временную сессию.
Регрессии на реальных отчётах — `tests/test_case_scenarios.py`; при отсутствии нужного
отчёта такой тест пропускается. Результаты живой проверки и ограничения —
в `docs/solution_status.md`. Это выбранная часть сценариев, не весь исходный файл.

## Сравнение моделей и задержек

`evaluate_quality.py` поддерживает `--model`, `--planning combined|legacy`,
`--reasoning-effort low|high|max`, `--limit N` (на каждый диалог) и `--summary-only`.
Последний флаг убирает тексты из консоли, но оставляет их в локальном JSON для оценки.
Модель меняется только внутри прогона: `.env` и рабочие сессии не затрагиваются.

```bash
PYTHONPATH=src:. uv run python -m benchmarks.evaluate_quality --live --dialogue feedback \
  --model glm-5.3-flash --planning combined --reasoning-effort low \
  --summary-only --output /tmp/counterparty-glm.json
```

Повторить одинаковый диалог для `qwen3.7-plus` и `deepseek-v4-flash-0731`.
`legacy` использует тот же роутер, но не исполняет его первоначальные разделы:
их повторно выбирает аналитический цикл. Проверки фактов одинаковы в обоих режимах.
У Qwen сохраняются флаги рассуждений из окружения; у DeepSeek 0731 и GLM используется
`reasoning_effort` ([DeepSeek](https://dslab.tech/ai/models/llm/deepseek-v4-flash-0731),
[GLM](https://dslab.tech/ai/models/llm/glm-5.3-flash)). Бюджеты токенов не увеличиваются
автоматически при смене модели, поэтому отдельно учитывайте прерванные ответы.

В `llm_calls` записываются этап, длительность SDK-вызова, расход токенов,
причина завершения либо класс ошибки; `llm_seconds` — сумма этих длительностей.
Это время с сетью и возможными повторами SDK, не скорость генерации и не TTFT.
Сообщения, ключи и скрытые рассуждения в метрики не попадают. Сохраняются модель,
режим планирования и бюджеты, чтобы результаты можно было сопоставить.
Сравнивайте также отказы, исправления, резервные ответы и смысл ответа вручную.
Одиночный прогон не доказывает устойчивую задержку, p95 или превосходство модели.

### Результат первого сравнения

Один и тот же диалог `feedback`, четыре сообщения, реальные отчёты и отдельные
временные сессии. Роутер: 1200 токенов; аналитический ответ: 2400; общий цикл: 120 с,
не включая роутер. Qwen без рассуждений, альтернативы — `reasoning_effort=low`.
Часть прогонов выполнялась одновременно; это предварительные наблюдения с сетью
и нагрузкой провайдера, не контролируемое измерение производительности моделей.

| Модель, объединённое планирование | Ответ после валидации | Медиана всех 4 сообщений | Диапазон |
|---|---:|---:|---:|
| Qwen3.7 Plus | 4/4 | 29,90 с | 29,11–36,17 с |
| GLM 5.3 Flash | 3/4 | 52,80 с | 24,41–78,58 с |
| DeepSeek V4 Flash 0731 | 1/4 | 119,36 с | 74,56–174,93 с |

У GLM один ответ целиком израсходовал 2400 токенов на рассуждения и оборвался.
У DeepSeek обрывались роутер и синтез; один цикл достиг общего таймаута.
Это результат **при текущих бюджетах**, не вывод о качестве моделей вообще.
Бюджеты не повышались: такое изменение потребовало бы отдельного сравнения.
Модель по умолчанию и локальный `.env` сохранены — Qwen3.7 Plus.

Отдельный парный прогон первых двух сообщений Qwen: медиана старого цикла 40,985 с,
объединённого — 35,945 с (около 12% разницы в этой малой выборке).
На первом запросе убраны два отдельных решения о чтении; число всех API-вызовов
сократилось с 6 до 5 из-за оставшихся исправлений и повторной верификации.
Минимальный путь из трёх вызовов наблюдался у GLM на первом сообщении.
Это не обещание трёх вызовов для каждого запроса.

Групповой контроль Qwen `case_group`: три компании → второй участник → возврат
к группе, 45,10 / 38,63 / 45,74 с. Фокус и условия сохранились; все три ответа
прошли через полную резервную сводку. Во всём `feedback` Qwen такой ответ был один.
`answered` и корректные ссылки не означают экспертного зачёта: ручной разбор Qwen
показал лишние предположения и слишком категоричные финансовые формулировки.
Качество текста и частые перегенерации остаются следующей задачей, они не объявлены
исправленными этим ускорением. Документы в этой итерации проверены автотестами,
не новым живым сравнением моделей. Проверки: ruff, mypy, 695 Python-тестов;
интерфейс не менялся и повторно не проверялся.
