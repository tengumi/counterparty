# Продуктовый контекст: проверка контрагентов в Альфа‑Бизнесе

Статус: рабочая версия 1, 3 сентября 2026 года.

## 1. Коротко

Мы предлагаем не «чат над PDF» и не новый банковский скоринг.

Продукт — рабочее пространство проверки, в котором предприниматель:

1. вводит ИНН нескольких известных кандидатов;
2. сравнивает их по единым критериям;
3. раскрывает факты и источники;
4. углубляется в неоднозначные сигналы с AI;
5. сохраняет ход проверки, документы, неизвестное и итог решения в проекте сделки.

Детерминированное ядро отвечает за факты и сравнение. AI объясняет выбранные данные. Ограниченный агент нужен только в сценарии, где он строит план углублённой проверки, обращается к разрешённым данным и документам и обновляет состояние проекта.

## 2. Проблема

Текущий сервис Альфы уже собирает значимые сведения и рассчитывает риск. Основная проблема находится после получения данных:

- отчёт выдаётся в PDF без краткого summary;
- компании проверяются последовательно;
- при shortlist из 5–20 компаний пользователь вручную сопоставляет разные разделы;
- итоговый светофор не всегда объясняет, что проверить дальше;
- результат проверки не становится продолжающимся рабочим контекстом сделки.

Рабочий problem statement:

> Предпринимателю или финансисту малого бизнеса нужно быстро сократить shortlist контрагентов и понять, какие факты, неизвестные данные и дополнительные проверки важны до принятия обязательств по сделке, не просматривая несколько длинных отчётов по отдельности.

## 3. Пользователь и контекст

Подтверждённый основной сегмент кейса:

- малый бизнес, ориентир кейсодателя — оборот до 20 млн ₽;
- предприниматель или финансист;
- приоритетные отрасли: строительство, логистика, производство;
- компании, активно работающие с поставщиками, подрядчиками и материальными ресурсами.

Основная точка входа в продукт: пользователь уже знает ИНН одного или нескольких кандидатов. Поиск рынка и каталог поставщиков находятся вне MVP.

### Поставщик и покупатель — разные решения

| Роль контрагента | Что поставлено на кон | Что особенно важно проверить |
|---|---|---|
| Поставщик/подрядчик | Аванс, срок, качество и непрерывность поставки | способность исполнить обязательство, релевантные суды, лицензии, финансовая устойчивость |
| Покупатель | Оплата после поставки или отсрочка | платёжеспособность, взыскания, долговая и судебная нагрузка |

Для MVP выбран поставщик перед авансом. Это гипотеза команды для демонстрации контекстной глубины, а не обязательное требование кейса.

Глубина проверки зависит от ставки: для небольшой обратимой сделки может быть достаточно базового индикатора; для крупного аванса, отсрочки или критичной поставки нужен evidence и дополнительная проверка.

Кейсодатель дополнительно подтвердил: универсальных «3–5 главных сигналов» нет — их значимость меняется в зависимости от цели проверки. Следовательно, цель нужна не для пересчёта банковского риска, а для приоритизации разделов, объяснений и следующих действий.

## 4. Текущее предложение Альфы

Публичный сервис «Проверка контрагента» позволяет заказать полный отчёт за 305 ₽. В подписке «Альфа‑Про» за 1 100 ₽ в месяц заявлено 15 полных отчётов и другие бизнес-сервисы.

По материалам Q&A текущий продукт работает так:

`ИНН → заранее агрегированные и ежедневно пересчитываемые данные → банковский риск и разделы отчёта → PDF → самостоятельная интерпретация пользователем`.

Расчёт риска уже существует. Создавать новый скоринг или менять банковский светофор не требуется.

Важно: светофор — комплаенс‑оценка и не является полной оценкой финансовой состоятельности. Поэтому зелёный светофор может сочетаться, например, с отрицательным капиталом. `riskLevel` и ЗСК также нельзя объединять в одну шкалу: банковский риск имеет зелёное, жёлтое, красное и серое состояния, ЗСК — зелёное и серое.

## 5. Opportunity

Слабое решение: добавить к PDF чат, который пересказывает его. То же действие пользователь может выполнить в сильной внешней модели.

Более сильная opportunity:

> Превратить разовый отчёт в доказательное рабочее пространство между сформированным shortlist и решением пользователя о дальнейшем взаимодействии.

Интерфейс не сводит все сведения к новому цвету, а удерживает несколько осей: комплаенс, финансовую устойчивость, судебно‑исполнительную нагрузку, опыт и полноту данных. AI помогает понять их значимость для выбранной цели.

Структурная ценность банка находится не в «собственной LLM», а в:

- актуальном нормализованном dossier;
- подтверждённой идентичности компании;
- единой семантике полей;
- источниках и дате среза;
- корректной обработке отсутствующих данных;
- контролируемых правах доступа;
- возможности использовать один доверенный слой в UI и через разрешённый MCP.

## 6. Место в пользовательском пути

| Этап | Роль продукта |
|---|---|
| Возникла потребность в поставщике/покупателе | Вне продукта |
| Поиск кандидатов и сбор предложений | Вне MVP |
| Сформирован shortlist, известны ИНН | Точка входа |
| Базовая проверка и сравнение | Детерминированное ядро |
| Уточнение цели проверки | Короткий контекст для приоритизации, без изменения банковского риска |
| Выбор компаний для углубления | Пользователь + интерфейс |
| Анализ неоднозначного риска | AI/ограниченный агент |
| Запрос документов и фиксация неизвестного | Рабочее пространство сделки |
| Итоговое решение | Человек |
| Договор, платёж, исполнение | Вне MVP |
| Мониторинг | Передача в существующий продукт Альфы |

### AS‑IS и TO‑BE

**AS‑IS:** возникли кандидаты → выбрать сервис → вводить ИНН по одному → скачать и изучить PDF → вручную сопоставить → принять решение вне продукта.

**TO‑BE:** создать проект → добавить 5–20 ИНН → получить сравнение → оставить shortlist → раскрыть evidence → углубить неоднозначные места → приложить документы → сохранить decision memo.

**Внешняя ветка:** подключить read-only MCP → выбрать разрешённый проект/компании → использовать актуальные данные Альфы в привычном AI → сохранить результат обратно только через подтверждённый сценарий.

## 7. Место AI и агента

AI не нужен для построения стандартного отчёта, сортировки, таблицы сравнения или показа банковского риска.

AI полезен, чтобы:

- объяснить выбранный показатель;
- сравнить выбранные факты;
- сформулировать возможные трактовки и ограничения;
- подготовить вопросы контрагенту;
- предложить дальнейшую проверку.
- сопоставить масштаб исполнительных производств и арбитражей с подтверждёнными финансовыми показателями, не используя универсальный порог «критично».

Агент появляется только тогда, когда существует продолжающийся проект сделки и агент:

- понимает цель проверки;
- определяет необходимые разделы и документы;
- вызывает несколько разрешённых read-only инструментов;
- сопоставляет данные отчёта и загруженных документов;
- ведёт список противоречий и неизвестного;
- обновляет decision memo при появлении новых данных.

Если убрать проекты, состояние, документы и инструменты, остаётся хороший AI‑чат, а не агент.

## 8. Влияние на retention

Нужно различать три уровня:

1. **Retention сервиса:** при следующей реальной потребности компания снова выбирает проверку Альфы.
2. **Retention Альфа‑Про:** проверка добавляет совокупную воспринимаемую ценность подписке и повышает вероятность продления.
3. **Retention банка:** связный путь «проверить → сохранить обоснование → продолжить работу» может укреплять роль Альфы как основного операционного банка.

Третий уровень — наиболее дальняя и пока недоказанная гипотеза. Рост посещений UI не является достаточной метрикой: MCP может уменьшить число входов в интерфейс и одновременно повысить использование подписки.

## 9. Конкурентная позиция

Альфа не обязана быть самым глубоким или самым дешёвым специализированным сервисом.

Рабочее позиционирование:

> Достаточная для основных задач проверка, уже включённая в общий контур бизнес-сервисов, с единым доступом к актуальным данным, сравнением и возможностью продолжить работу в привычном AI.

Для редких и простых проверок Альфа может заменить отдельный point solution. Для сложных расследований она может служить первым фильтром перед СПАРК, Контур.Фокусом или профессиональной проверкой.

## 10. Что должен доказать MVP

MVP не доказывает долгосрочный retention. Он должен показать более близкие предпосылки:

- сравнение нескольких компаний полезнее последовательного чтения PDF;
- пользователь быстрее находит значимые различия;
- результат содержит не только summary, но и проверяемые следующие действия;
- AI не изменяет канонические факты и не скрывает отсутствие данных;
- агентная вертикаль продолжает проект при добавлении нового документа;
- UI и MCP используют один разрешённый слой данных.

Связанные документы:

- `01_EVIDENCE_REGISTER.md` — что является фактом, гипотезой или неизвестным;
- `02_DETERMINISTIC_PRODUCT_LAYER.md` — что работает без LLM;
- `03_AGENT_AND_DEAL_WORKSPACE.md` — конкретный агентный сценарий и память;
- `04_RETENTION_MVP_AND_VALIDATION.md` — метрики, гипотезы и план MVP;
- `05_TRUST_LEGAL_AND_MCP_BOUNDARIES.md` — ограничения доверия, данных и внешнего доступа.
- `06_DESIGN_SURFACE_BRIEF.md` — ТЗ дизайнеру на ключевые поверхности.
- `07_MARKET_ECOSYSTEM_AND_ALTERNATIVES.md` — место в Альфа‑Бизнесе, Альфа‑Таргет и конкурентные альтернативы.
