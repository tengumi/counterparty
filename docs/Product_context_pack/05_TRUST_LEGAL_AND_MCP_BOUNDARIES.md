# Доверие, юридические границы и MCP

Документ не является юридическим заключением. Финальные формулировки, состав данных и режим внешней передачи должны быть согласованы с юридической службой и информационной безопасностью банка.

## 1. Дисклеймер — только один слой защиты

Фраза «результат не является юридической консультацией» полезна, но не делает небезопасный вывод безопасным. Пользователь может проигнорировать предупреждение, особенно если рядом показан категоричный вердикт.

Поэтому защита должна находиться в самой структуре продукта:

- факты отделены от AI‑интерпретации;
- AI‑контент явно маркирован;
- у каждого существенного утверждения есть источник и дата;
- отсутствие записи не трактуется как отсутствие риска;
- банк не гарантирует надёжность контрагента;
- зелёный комплаенс‑светофор не маркируется как общая финансовая надёжность;
- решение принимает пользователь;
- высокорисковый вывод можно передать человеку на пересмотр;
- есть канал исправления ошибочных или устаревших сведений.

## 2. Предлагаемая модель согласия

1. При первом использовании — понятные условия и границы AI.
2. В интерфейсе — постоянная компактная маркировка AI‑интерпретаций.
3. Около рискованной рекомендации — контекстное предупреждение, а не общий баннер.
4. Перед сохранением итога — подтверждение, что решение принял пользователь.
5. Перед подключением внешнего AI — отдельный consent со scopes и перечнем передаваемых данных.

Не следует требовать формальную «подпись» при каждом вопросе: это создаёт habituation и не заменяет безопасный дизайн.

## 3. Язык продукта

Допустимый стиль:

> В доступных данных на указанную дату обнаружено снижение выручки и такие-то судебные события. Для сделки с авансом это основание запросить следующие подтверждения.

Недопустимый стиль:

> Компания ненадёжна. Работать с ней нельзя.

До отдельного согласования запрещены обещания:

- «контрагент безопасен»;
- «банк рекомендует поставщика»;
- «риск отсутствует»;
- «решение соответствует требованиям законодательства»;
- «проверка гарантирует должную осмотрительность».

## 4. Данные

Разрешённый базовый контур:

- поля текущего отчёта, которые уже разрешено показывать клиенту;
- дата среза;
- источник;
- технический идентификатор evidence;
- пользовательские документы внутри его проекта при отдельном основании.

По умолчанию исключаются:

- операции, счета и остатки контрагента;
- факт обслуживания контрагента в банке;
- внутренние AML/115‑ФЗ события и расследования;
- внутренние причины скоринга, не разрешённые к раскрытию;
- данные других клиентов;
- лицензируемые данные стороннего поставщика, запрещённые к передаче;
- derived summary, если исходное поле нельзя выдавать напрямую.

Публичность исходного факта сама по себе не означает разрешение на его массовую внешнюю выгрузку.

## 5. Read-only MCP

MCP — второй интерфейс к разрешённому слою, а не обход банковских политик.

Минимальные инструменты:

```text
compare_counterparties(ids, sections)
get_counterparty_evidence(id, evidence_ids)
get_project_context(project_id)
```

Возможный четвёртый инструмент после согласования:

```text
get_project_open_questions(project_id)
```

Требования:

- OAuth, инициированный клиентом;
- минимальные scopes;
- read-only по банковским данным;
- ограничение количества компаний;
- аудит вызовов;
- отзыв доступа;
- короткоживущие токены;
- запрет массовой выгрузки;
- явный отказ на запрещённые поля;
- контроль prompt injection из документов;
- политика хранения у внешнего AI‑провайдера.

Разрешение клиента на вызов сервиса не заменяет правовое и договорное основание для передачи сведений третьей стороне.

## 6. Человеческий контроль

Человек обязателен для:

- окончательного решения о контрагенте;
- трактовки спорного юридического обстоятельства;
- утверждения нестандартных условий сделки;
- внешней отправки сообщения или документа;
- платежа;
- исправления или оспаривания сведений;
- пересмотра высокорискового AI‑вывода.

## 7. Ориентир Банка России

Кодекс этики в сфере AI на финансовом рынке рекомендует человекоцентричность, прозрачность, безопасность, контроль качества и ответственное управление рисками. В частности: информирование об использовании AI, маркировку генеративного контента, возможность отказа и человеческого пересмотра, проверку данных и моделей, защиту конфиденциальности и регистрацию риск-событий.
