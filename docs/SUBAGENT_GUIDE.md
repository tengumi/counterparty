# Единая инструкция субагенту

Эта инструкция применяется ко всем исследовательским, реализационным и
проверочным субагентам проекта. Главный агент не копирует её целиком в каждое
поручение: он передаёт task ID, outcome, ownership и ссылки на нужные материалы,
а также указывает работать по этому файлу.

## 1. Начало задачи

1. Работай только в выданном главным агентом Git worktree и текущей task-ветке.
   Не переключай ветку, не создавай другой worktree и не меняй основной
   worktree репозитория.
2. Прочитай `AGENTS.md`, это руководство, короткое поручение и только указанные
   в нём разделы Specs/артефакты. Не загружай весь корпус проекта.
3. Проверь `git status --short`, текущую ветку и существующий task-checkpoint.
   Чужие изменения не исправляй и не удаляй.
4. До изменений запиши в checkpoint: цель, ownership, зависимости, план из
   2–5 проверяемых шагов и первый следующий шаг.

Путь checkpoint:
`docs/checkpoints/tasks/<TASK_ID>.md`. Для каждой задачи используется отдельный
файл, поэтому параллельные агенты его не делят.

## 2. Границы работы

- Редактируй только область, указанную в поручении. Если требуется shared-файл,
  миграция, contract или чужой composition root — остановись на безопасной
  границе и сообщи главному агенту.
- Specs, `AGENTS.md`, `NEXT_STEPS.md`, `README.md` и общий WORK_PLAN не меняй,
  если это не является явным outcome задачи.
- Артефакты дизайнера и исходный mock JSON не редактируй и не копируй.
- Не расширяй архитектуру новыми сервисами, протоколами или хранилищами.
- Не оставляй важное состояние только в сообщении, stash, незакоммиченном
  generated-файле или памяти процесса.

## 3. Прогресс и восстановление

Работай короткими завершёнными шагами. После discovery, каждого существенного
изменения, проверки и перед потенциально долгой/рискованной операцией:

1. обнови task-checkpoint;
2. сделай небольшой осмысленный commit;
3. отправь главному агенту короткий progress update.

Нормальный commit должен быть собираемым и проверенным в пределах шага. Если
работу приходится остановить между устойчивыми состояниями, разрешён отдельный
`wip(<scope>): <TASK_ID> checkpoint` commit в task-ветке. В checkpoint явно
укажи failing checks и почему этот commit нельзя интегрировать. WIP не попадает
в целевую ветку как готовый результат.

Не используй stash как checkpoint. Не объединяй много несвязанных изменений в
один commit. Не переписывай опубликованную task-ветку force push/reset без
поручения главного агента.

После перезапуска работа поднимается так:

1. открыть выданный worktree;
2. прочитать task-checkpoint;
3. выполнить `git status --short` и `git log -5 --oneline`;
4. повторить последнюю указанную проверку;
5. продолжить с поля «Следующее действие».

Если checkpoint и код расходятся, доверяй Git diff/tests, исправь checkpoint и
сообщи главному агенту о расхождении.

## 4. Формат task-checkpoint

Файл остаётся компактным и обновляется вместо накопления журнала:

```markdown
# <TASK_ID> — <название>

- Status: discovery | implementation | verification | blocked | done
- Branch: agent/<task-id>-<slug>
- Worktree: .worktrees/<task-id>-<slug>
- Owner scope: <пути>
- Depends on: <task IDs / commit>
- Last commit: <sha или none>

## Готово

- <проверяемый результат>

## Текущее состояние

- <что работает>
- <что временно не работает и почему>

## Проверки

- `<command>` — passed/failed/not run: <причина>

## Решения и допущения

- <только то, что нужно интегратору>

## Следующее действие

<один конкретный шаг или команда для быстрого продолжения>
```

Не вставляй полные логи, diff или пересказ Specs. Для исследования сохраняй
только решение, ссылку на первичный источник, версию/дату, ограничение и
следующий шаг.

## 5. Проверка и handoff

Перед статусом `done`:

- выполни проверки, указанные в поручении и `AGENTS.md`;
- просмотри `git diff` и убедись, что ownership не нарушен;
- обнови checkpoint до `done`, указав финальный commit;
- оставь task-ветку и worktree в чистом состоянии;
- отправь главному агенту handoff строго в формате:

```text
Result: что теперь работает.
Commits: SHA и назначение.
Files: изменённые области.
Checks: команды и результат.
Assumptions/Risks: только непроверенное или блокирующее.
Integration: порядок merge/cherry-pick и нужные follow-ups.
```

Субагент не объявляет пользовательский срез принятым и не запускает следующую
задачу самостоятельно. Главный агент интегрирует ветви, назначает verifier и
проводит review результата с пользователем.

## 6. Что делает verifier

Verifier получает другой worktree либо чистую интеграционную ветку, task ID,
acceptance и commits реализации. Он не переписывает реализацию молча:

1. воспроизводит заявленные команды;
2. проверяет границы, негативные случаи и отсутствие случайных изменений;
3. при небольшом дефекте возвращает точное замечание; исправление делает
   implementer через follow-up;
4. фиксирует verdict `pass` / `pass with limitations` / `fail` и evidence
   проверки в собственном checkpoint или сообщении главному агенту.
