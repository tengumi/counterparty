# 01. Целевая архитектура MVP

Версия 1.1 · 05.09.2026. Навигация: [индекс](00_OVERVIEW_AND_INDEX.md).

## 1. Назначение и границы

Продукт снимает с предпринимателя работу по выбору значимых разделов отчёта, сопоставлению фактов и формулированию следующих вопросов перед сотрудничеством. Интерфейс, модель и данные работают в одном проекте проверки. Сравнение нескольких компаний — дополнительный путь в этом же объекте.

Критерий архитектуры: один сквозной сценарий от вопроса до обоснованного результата, с доступными источниками, сохранением состояния и продолжением после нового документа. Не требуется распределённая банковская production-платформа.

## 2. Развёртываемые части

| Компонент | Входит | Не входит |
|---|---|---|
| Web | Два основных экрана, материалы, чат, адаптер assistant-ui | Прямой доступ к БД, модельные ключи, выполнение MCP из браузера |
| UI Backend | Проекты, документы, условия, решение пользователя, read API отчётов, расчёты | LLM-пересказ в детерминированном summary, оркестрация агента |
| Agent Service | RPC, активные запуски, контекст, Deep Agents, внутренние инструменты проекта, поток UI | Пересчёт банковского светофора, платежи, произвольный SQL от модели |
| MCP | Три read-only инструмента отчётов, договорённая семантика, лимиты | Чаты, память, пользовательские документы, банковские операции |
| PostgreSQL | Две схемы, история данных, checkpoints | Хранение модельных ключей в строках проектов |
| Файловое хранилище | Оригиналы загруженных документов | Доступный агенту произвольный диск хоста |

Каждая развёртываемая часть имеет собственный Dockerfile и сначала запускается
самостоятельно. Целевой локальный контур — Docker Compose, один экземпляр
каждого сервиса, reverse proxy, один PostgreSQL и постоянный volume файлов;
общий compose собирается после готовности отдельных образов. S3-совместимый
storage — через интерфейс без обязательного MinIO в первом демо. Redis,
Kubernetes, отдельный API gateway, Celery и брокер не обязательны.

## 3. Стек и структура кода

- Python 3.13, asyncio, FastAPI, Pydantic v2, Dishka; SQLAlchemy 2 async + psycopg 3, Alembic.
- LangChain — провайдеры моделей и адаптеры; LangGraph — состояние и исполнение; Deep Agents — агентный harness. Не создавать параллельный самописный цикл вызова инструментов.
- assistant-stream — транспорт состояния встроенного чата; assistant-ui — готовая React-логика и primitives.
- FastMCP — отдельное ASGI-приложение, HTTP transport.
- React + TypeScript strict + Vite, Core Components, glyph-иконки Альфы, React Router, TanStack Query.
- pytest, Ruff check/format с Google-style docstrings, strict mypy; uv и lockfile как default управления Python-зависимостями.

Монорепозиторий: `apps/web`, `services/ui_api`, `services/agent`, `services/mcp`, `packages/contracts`, `packages/domain`, `packages/storage`, `migrations`, `scripts/import_reports`, `tests`, `docs`. Это структура будущего репозитория; данный набор не содержит реализацию.

В shared-пакетах — типы, проверяемые вычисления, прикладные операции и репозитории. У каждого процесса свой набор зависимостей, credentials и composition root. Общий пакет не должен выполнять сетевые запросы или миграции при импорте.

## 4. Владение состоянием и права

| Данные | Кто пишет | Кто читает |
|---|---|---|
| reports: исходный и нормализованный отчёт | Импортёр отдельной DB-ролью | UI Backend и MCP с SELECT |
| workspace: проект, состав компаний, документы, подтверждённые условия | UI Backend; разрешённые внутренние действия агента через общий прикладной слой | UI Backend, Agent Service после проверки доступа |
| workspace: пользовательское решение | Только операция UI Backend с автором-пользователем | UI Backend, Agent Service |
| workspace: AI-выводы, вопросы, служебные запуски | Agent Service | UI Backend, Agent Service |
| workspace: checkpoints и опциональный Store | Штатный PostgreSQL backend LangGraph | Agent Service через API фреймворка |

Права схем не заменяют проверку владельца проекта. Все запросы scoped по `tenant_id` и `project_id`. MCP не имеет доступа к `workspace`. Агент не ходит в `reports` напрямую: получает сведения через MCP. UI получает детерминированные сведения через свой API. Одинаковые вычисления обоих путей используют shared domain functions.

UI Backend не декодирует внутренний формат checkpoints. Для чтения UI используется сохранённая публичная проекция разговора и запуска, обновляемая Agent Service. Это производное представление; новые команды не восстанавливают graph из браузерной истории.

## 5. Идентификаторы и контракты

`project_id` — сохраняемая проверка вокруг задачи; `thread_id` — один из сохраняемых диалогов/рабочих сессий проекта; `run_id` — исполнение одной команды; `client_request_id` — защита от повторной отправки; `report_id` — неизменяемый снимок; `company_id` — идентичность компании; `document_id` — файл проекта; `artifact_id` и `version` — AI-вывод; `decision_id` — запись пользователя; `evidence_ref` — точный источник.

UUID генерируются сервером. ИНН — строка, не число. `tenant_id`, права и разрешённые `thread_id` выводятся из серверной аутентификации и связей, не доверяются аргументам модели.

API-контракты — отдельные Pydantic-модели; ORM не выдаётся наружу. REST описывается OpenAPI. RPC описывает команды и публичное состояние поверх assistant-stream; это не JSON-RPC 2.0. TypeScript-типы генерируются из опубликованных схем или проверяются контрактными тестами.

## 6. Поток запроса

1. UI сохраняет проект и начальный контекст через REST; создание проект+thread mapping атомарно и идемпотентно. Создавать проект вручную пользователь не обязан.
2. UI отправляет команду на `/rpc/agent/chat`, включая project/thread и request ID; Agent Service проверяет права, актуальность и активный run.
3. Агент восстанавливает checkpoint; добавляет новую команду и актуальный контекст проекта. Не дублирует уже применённые сообщения.
4. Deep Agents отвечает сразу либо выбирает MCP/внутренние инструменты. Факты, документы и предположения имеют разное происхождение.
5. Agent Service обновляет публичное состояние и передаёт его через assistant-stream. Приватные prompts, секреты и внутренние рассуждения не входят в поток.
6. Результат, вопросы и checkpoints сохраняются. UI читает актуальные материалы и показывает результат. Решение пользователя записывается отдельным REST-действием.

Начало с файлом: проект создаётся скрыто, файл загружается, затем первая команда связывается с этим документом. При неуспешной загрузке проект остаётся доступным черновиком; сообщение не отправляется без явного действия пользователя.

## 7. Согласованность, изменения и ошибки

Длительное выполнение анализирует зафиксированную `context_version` проекта и конкретные версии отчётов. Изменения условий или документов во время run увеличивают версию проекта. Перед публикацией вывод сравнивается с текущей версией: при расхождении показывается «Вывод сделан для прежних условий» и предлагается пересмотр. Новый вывод не выдаётся как актуальный без этой проверки.

Не держать транзакцию открытой на время LLM/MCP. Сначала коротко загрузить контекст, затем выполнить внешние вызовы, затем коротко сохранить результат с optimistic concurrency. Запись решения пользователя всегда отдельна от записи предложения агента.

Закрытие вкладки не отменяет запуск. Поток UI и task агента имеют разный lifecycle. В MVP один Agent Service; после перезапуска прерванные runs получают явный статус и могут быть продолжены с checkpoint. Автоматическое распределённое восстановление не обещается. Наличие сохранённого checkpoint не равно гарантии исполнения ровно один раз.

## 8. Доступ и внешний AI

В MVP — явный demo login/server-issued session с tenant scope; не имитация реальной авторизации Альфы. Секреты только на backend. У внутреннего MCP служебная аутентификация и разрешённый набор данных. Авторизация внешнего AI и реальная банковская интеграция не входят в основной delivery.

Внешний MCP может передать только отдельно разрешённую проекцию отчёта. Пользовательские документы и скрытые банковские данные туда не попадают по умолчанию. Read-only и OAuth являются механизмами контроля, а не доказательством юридической допустимости передачи.

## 9. Границы расширения

Не включать каталог по рынку, мониторинг, платежи, рассылку контрагентам, новый скоринг, автономные внешние действия, векторную БД без доказанной необходимости. Добавление очереди/worker допускается при реальной потребности в нескольких процессах и восстановлении после падения, без изменения продукта и API-контрактов.

## 10. Уточнение 1.1: сессии и навыки

Проект содержит 1..N threads. Первый создаётся автоматически; дополнительные — «Новый чат». У каждого отдельные history/checkpoints/run ownership; общие данные проекта подключаются явно и с версиями. Не подмешивать полную историю соседних чатов. Доступ к общему артефакту не делает его вывод подтверждённым условием сделки.

UI Backend управляет списком/названиями/архивированием чатов; Agent Service — исполнением и состоянием. RPC разрешает один активный run на thread, но принимает дополнительные сообщения в persistent inbox. Состав проекта во время параллельных чатов защищён context_version и обычной конкуренцией записей.

Skills — штатный механизм Deep Agents с read-only каталогом готовых инструкций. Внутренний skill adapter вызывает проверенные библиотеки в bounded worker threads; CPU/GIL-bound или непотокобезопасный путь вынесен в изолированный process. Не создавать четвёртый бизнес-сервис только ради skills. По-прежнему запрещены произвольный shell и доступ к чужим файлам.
