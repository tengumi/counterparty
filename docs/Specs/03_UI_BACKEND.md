# 03. Backend для UI и детерминированный слой

Версия 1.1 · 05.09.2026. [Индекс](00_OVERVIEW_AND_INDEX.md) · [Контракты](10_SYSTEM_CONTRACTS.md).

## 1. Назначение

FastAPI-сервис обслуживает продуктовые ресурсы и все результаты, которые вычисляются без модели. Он не вызывает LLM для обычной карточки, сортировки, сравнения цифр или статуса проекта. Работает асинхронно, использует Pydantic, Dishka, SQLAlchemy async и общий domain-пакет с MCP.

## 2. Прикладные операции

| Операция | Поведение |
|---|---|
| Создать проверку | Скрыто при первой отправке; title, tenant, project_id, thread_id, context_version; request ID защищает от дублей |
| Список/открытие проверок | Свои проекты, сортировка по активности, cursor pagination, проектный статус и краткий незакрытый вопрос |
| Переименовать/удалить | Переименование не меняет задачу; удаление требует UI-подтверждения и корректной отмены run |
| Добавить компанию | По ИНН/выбранному результату локального поиска; привязать конкретный report_id |
| Добавить списком | 2–20 компаний; per-item результат, без молчаливого обрезания и повторов |
| Удалить компанию из проекта | Исключить из текущего состава; исторические источники не теряются |
| Условия сделки | Роль, предмет, сумма, валюта, аванс/порядок оплаты, сроки, приоритет; источник и подтверждённость |
| Документы | Загрузка, получение статуса/метаданных, доступ к оригиналу/фрагменту, удаление |
| Сводка/сравнение | Типизированные факты, расчёты, доступность, даты и evidence refs |
| Решение пользователя | Сохранить вариант, обоснование, условия, автора, версии оснований; история изменений |

Список конкретных HTTP-маршрутов и payloads — единственный канонический реестр в 10_SYSTEM_CONTRACTS.md. Не плодить альтернативные endpoints в frontend и агенте.

## 3. Summary: что показывать первым

Сводка имеет фиксированную структуру, но не универсальную итоговую рекомендацию:

1. Идентичность компании, дата регистрации и статус из отчёта.
2. Исходный риск банка, отдельно ЗСК, с подтверждённой политикой отображения.
3. Последний доступный финансовый период и сопоставимые предыдущие: выручка, прибыль при наличии, капитал, деньги по отчётности, дебиторская/кредиторская задолженность.
4. Действующие производства: количество записей, сумма известных amounts, количество без суммы, даты.
5. Суды: суммы/количества по роли и состоянию, отдельно годовые агрегаты.
6. Деятельность, лицензии, госзакупки и связанные компании при наличии.
7. Отсутствующие разделы, неодинаковые периоды, предупреждения о точности и возрасте снимка.

UI может сворачивать разделы. Нельзя скрыть существенный факт только потому, что score банка зелёный. «Куда посмотреть» — наблюдаемые факты по версионируемым правилам; «что это значит для аванса именно в этой сделке» — отдельная интерпретация агента.

## 4. Детерминированные вычисления

| Вычисление | Правило |
|---|---|
| Аванс | price × advance_percent / 100; округление денежных значений до 2 знаков, валюта обязательна |
| Разница предложений | Сравнивать отдельно цену и аванс при одинаковой валюте; не делать валютную конверсию без курса и даты |
| Изменение показателя | Абсолютная разница для двух известных периодов; процент только при допустимом знаменателе и явной формуле |
| Годовая динамика | Только соседние годы; несоседние подписать как изменение между указанными годами |
| Действующие ИП | active=true; известную сумму суммировать отдельно от числа пропусков; это «известная сумма», не полный долг |
| Отношение взысканий к масштабу | Сопоставить периоды и смысл базы; отношение к капиталу при equity≤0 не вычислять как обычный процент |
| Суды | Не суммировать статусные и годовые агрегаты друг с другом: возможен двойной счёт |
| Комплектность | source_state и warnings; ошибка парсинга не становится отсутствием события |

Чистые активы и equity не считать юридически/методологически тождественными без согласованной формулы. В MVP допустимо показывать капитал из отчётности как явно названный ориентир масштаба. Банковские и пользовательские риски не сводить в новый балл.

Defaults API: сравнение до 20 компаний, сортировка стабильная; неизвестное не считается наихудшим числом. При несопоставимости годов показываем по каждой компании её период и предупреждение. При частичной ошибке возвращаем остальные доступные результаты с per-company статусом.

## 5. Документы и контекст

Форматы: PDF, PNG, JPEG, TXT, MD, CSV, TSV, XLSX, DOCX, HTML, JSON, XML; до 10 МБ на файл, до 10 активных файлов на проект. Это defaults MVP, согласованные с UX. Проверять MIME/сигнатуру, размер, имя, принадлежность проекта; storage key генерирует сервер. Файлы не сохранять по пользовательскому пути.

Статусы: uploaded → processing → ready / failed; deleted — недоступен. Хранить исходный документ и извлечённые фрагменты. Проверка MIME/размера выполняется сразу. Семантическое чтение файла запускается через skill (см. 11), а не в обход него. PDF с текстовым слоем разбирается без LLM; для сканов/изображений используется выбранный OCR или модель с vision. Библиотека извлечения выбирается на первом реальном fixture; архитектурный контракт одинаков. Если распознавание невозможно, показать точную ошибку и предложить вставить текст. Нельзя притворяться, что изображение прочитано.

Разбор не блокирует event loop; синхронная библиотека вызывается в ограниченном thread pool, CPU-тяжёлый разбор — в process pool при необходимости. Сетевая OCR/vision-обработка асинхронна, с timeout. Проверка допустимости передачи документов провайдеру должна быть явной; для демо используются синтетические материалы.

Для цитирования: документ и typed locator — страница PDF, лист/диапазон XLSX, абзац/ячейка таблицы DOCX, строки текста; offset/bbox только при реальном наличии. Файлы и фрагменты доступны агенту через внутренний repository/storage adapter с проверкой project scope; внутренний HTTP-запрос к UI Backend ради каждого фрагмента не обязателен.

## 6. Условия и выводы

У каждого факта `provenance_ref` и статус: user_confirmed / extracted_unconfirmed / inferred. Сведения, явно сообщённые пользователем, можно считать подтверждёнными им; извлечённые из документа значимые условия агент предлагает подтвердить. Нельзя смешать «80% аванса» Компании А с предложением Компании Б.

Изменение условий, добавление/удаление материала увеличивает `context_version`. Зависимые AI-выводы отмечаются outdated. Изменение заголовка проекта не меняет контекст сделки. Старое решение пользователя сохраняется с пометкой о новых сведениях. История не переписывается.

## 7. Безопасный отказ и эксплуатация

Проверять tenant/project ownership для всех операций, включая file download и evidence resolution. Ошибки API содержат понятный код и request_id, но не traceback/SQL. Нельзя принимать actor_user_id из тела как подтверждение авторства. Логи не должны содержать содержимое пользовательских документов и секреты по умолчанию.

При недоступном агенте REST-карточка, документы и детерминированное сравнение доступны. При недоступном разделе у компании показывается частичный результат. Ни ошибки сети, ни таймауты не интерпретируются как «рисков нет».

## 8. Приёмка

- Первая реплика создаёт ровно одну проверку; повтор запроса не дублирует ресурс.
- Сводка и сравнение совпадают с MCP по одинаковым report_id и версии правил.
- Доступны минимум пять компаний в сравнении, предусмотрено до 20.
- Удаление/изменение материала делает зависимый вывод неактуальным.
- Пользователь может сохранить своё решение, в том числе несогласие с AI.
- Файлы, источники и проекты другого пользователя недоступны.

## 9. Дополнение 1.1: чаты, артефакты и расширенные документы

Добавить CRUD рабочих сессий/чатов в проекте: создать, список, переименовать, архивировать, открыть сохранённое состояние. Первый чат создаётся вместе с проектом. Несколько чатов не означают несколько копий documents/facts. Удаление/архивирование не отменяет run молча: для удаления сначала явная отмена, для архива предложить подтверждение при активной работе.

Добавить attachment resolver для артефактов: проверить project ownership, существование версии и locator; вернуть компактную метаинформацию для composer и содержимое для агента. Разрешены артефакт целиком и конкретный раздел. Нельзя принимать URL или произвольный серверный path как artifact attachment.

Пайплайн файлов: upload/проверки → uploaded → skill execution → processing → ready/failed. Документ может быть принят до его анализа. Открытие агентом нового файла запускает соответствующий skill; повторное чтение того же hash/parser_version использует cached extraction с честным trace «Использую уже прочитанный документ». Автоматическая подготовка после upload, если включена, вызывает тот же skill executor, а не второй несогласованный парсер.

Старые .doc, .odt, .rtf обрабатываются через adapter изолированной конвертации (например, LibreOffice headless) при наличии зависимости. Это process, не thread; при отсутствии адаптера интерфейс честно предлагает DOCX/TXT. Основная обязательная Word-поддержка — DOCX. Для архивных Office-контейнеров ограничить распакованный объём, число листов/строк и вложений; макросы и внешние ссылки не исполнять.
