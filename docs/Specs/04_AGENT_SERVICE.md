# 04. Агент: контекст, инструменты, память и выполнение

Версия 1.1 · 05.09.2026. [Индекс](00_OVERVIEW_AND_INDEX.md) · [Контракты](10_SYSTEM_CONTRACTS.md).

## 1. Назначение и принятый стек

Сервис отвечает на деловой вопрос предпринимателя и выполняет необходимые проверки доступных данных. Python 3.13, FastAPI, asyncio, Dishka, Pydantic, LangChain, LangGraph, Deep Agents, assistant-stream. Это собственный компактный сервис; официальный Agent Server и LangServe не используются. Вспомогательные функции фреймворка берём готовыми, собственный agent loop не пишем.

Провайдер и model ID задаются конфигурацией; в описании кейса допускается любая модель, предпочтительны Qwen или GPT-OSS. Доступный API и модель для реального демо команда ещё должна назвать. Для выбора проверить tool calling, русский язык, structured output и работу с требуемой длиной контекста; vision может быть отдельным адаптером чтения документов.

Агентность видна там, где следующий шаг зависит от новых фактов: агент уточняет существенное условие, выбирает разделы/документы, проверяет неоднозначность, сохраняет вопросы и обновляет результат. Для простого объяснения одной строки достаточен один ответ модели; не заставлять его вызывать инструменты ради демонстрации.

## 2. Поведение

1. Понять, зачем пришёл пользователь: проверить поставщика, покупателя с отсрочкой, подрядчика, сравнить кандидатов или объяснить конкретный факт.
2. Уточнять только сведения, способные изменить вывод. Обычно один-два связанных вопроса, без обязательной анкеты и отдельного согласования плана.
3. Сначала использовать уже сохранённые условия и доступные документы. Не спрашивать повторно то, что известно; противоречащие версии предъявить пользователю.
4. Если задача требует дополнительных фактов — самостоятельно выбирать инструменты и последовательность в пределах разрешений.
5. Давать вывод относительно задачи, основания, неизвестное и следующий конкретный шаг. Не обещать надёжность или гарантированное исполнение.
6. При нескольких компаниях разрешать местоимения только при однозначном адресате; иначе уточнить.
7. При нехватке данных разрешать завершение «Нужно больше сведений»; не вести пользователя по бесконечному циклу загрузки файлов.

Сила модели не определяется количеством вызовов. Не навязывать subagents, shell, браузер или code interpreter; включать только под проверенный сценарий и с ограничениями.

## 3. Сборка контекста

| Слой | Содержание | Авторитетность |
|---|---|---|
| Политика | Задача, доступные инструменты, границы, правила источников | Серверная конфигурация |
| Знания предметной области | Пояснения полей, ОКВЭД, корректировки Q&A, формулы и ограничения | Версионируемый справочник, не выдуманный нормативный акт |
| Проект | Цель, роль контрагента, сумма, оплата, сроки, приоритет, текущие компании | Каждое значение с источником и подтверждённостью |
| Диалог | Восстановленное состояние, последние сообщения, summary длинной истории | LangGraph checkpoint; summary не заменяет источники |
| Материалы | Список файлов, готовность, назначение, открытые вопросы | Метаданные проекта |
| Сведения | Компактная сводка по выбранным report_id | MCP; подробности доступны инструментом |
| Результат | Последний AI-вывод, решение пользователя, что изменилось | Отдельные сущности с версиями |

На каждую новую команду загружается checkpoint и актуальная версия проекта; не строить историю с нуля из произвольного browser state. Полные JSON и все документы не подкладываются автоматически. Небольшие разделы/3–5 кратких отчётов могут быть переданы сразу, если укладываются в бюджет; большие списки производств читаются с фильтрами и пагинацией.

Defaults MVP: до 20 компаний в проекте; лимиты context tokens, output tokens, tools calls, duration задаются конфигурацией модели. До замеров принять max 12 tool calls, 120 секунд на run, максимум 3 одновременных read-вызова; это инженерные defaults, не исследованные продуктовые нормы. Лимит достигнут — честный частичный результат с сохранением состояния. Уточнение пользователю завершает/приостанавливает работу, не удерживает LLM в ожидании.

## 4. Память

Использовать AsyncPostgresSaver/поддерживаемый async checkpointer. Он сохраняет graph state диалога. Не создавать свою сериализацию состояния исполнения. Между turns приложение восстанавливает тот же thread_id.

Подтверждённые условия, документы, вопросы и решения лежат в workspace. Deep Agents filesystem backend ограничивается проектом/диалогом. Допускаются виртуальные рабочие файлы и их сохранение через штатный backend. Нет доступа к корню ОС, shell, чужим проектам или переменным окружения через file tools.

Store — опционально, если нужен механизм памяти вне thread. В MVP отсутствует скрытое извлечение глобальных предпочтений между проектами. Файл со сводкой помогает контексту, но при конфликте приоритет у подтверждённого факта и его источника. Удаление проекта удаляет его память и доступные файлы.

## 5. Инструменты

**Через MCP:** get_company_overview, get_report_section, compare_companies — контракты в 05/10. Агент получает только данные разрешённых reports, не SQL.

**Внутренние инструменты продукта:**

| Инструмент/операция | Вход | Результат и граница |
|---|---|---|
| list_project_documents | project scope из сервера | Метаданные готовых/обрабатываемых файлов |
| read_document_fragment | document_id, page/fragment IDs, лимит | Текст/изображение с provenance; проверка принадлежности |
| propose_project_facts | Значения и ссылки на реплику/файл | Подтверждённое сообщение пользователя или неподтверждённое извлечение; история версий |
| update_open_questions | Вопросы, причина, статусы, источники | Сохраняемый список значимых неизвестных |
| save_analysis_artifact | Структурированный вывод с context_version и refs | Новая версия AI-вывода; не пользовательское решение |
| calculate_transaction_values | Типизированные сумма/аванс/сравнимые предложения | Decimal-расчёт общими domain functions |

Эти имена — предлагаемые внутренние функции, не дополнительные MCP endpoints. Модель не может подставить чужой project_id: scope инжектируется сервисом. Добавление компании агентом допускается только при явном пользовательском запросе и однозначном ИНН; применяются лимит и обычные прикладные проверки.

## 6. Знания, которые обязательно дать агенту

- Коды ОКВЭД передаются с описаниями. «Массовые ОКВЭД» по уточнению заказчика — сигнал распространённости некоторых видов деятельности среди проблемных компаний, а не порог количества кодов у одной компании. Это повод уточнить, не доказательство нарушения.
- Банковский светофор — комплаенс-оценка. Он может быть зелёным при отрицательном капитале; финансовая состоятельность оценивается отдельно.
- ЗСК и банковский риск не одно и то же. Сырые YELLOW/RED ЗСК сохраняются, отображение — по отдельной подтверждённой политике.
- Производство даже на небольшую сумму не является автоматическим запретом. Важны сумма, давность, масштаб, активность и задача. Не делить на нулевые/отрицательные чистые активы и не выдавать необычный процент за норму.
- Блокировка ФНС — отрицательный фактор; известная кратковременная блокировка не доказывает невозможность любых платежей. Из флага без дат не выводить длительность.
- Переезд и уменьшение уставного капитала — разные изменения; проверить контекст, не называть банкротством.
- Нет универсальных 3–5 решающих сигналов: поставщик с авансом и покупатель с отсрочкой требуют разных акцентов.
- Данные о деньгах из годовой отчётности не означают текущий остаток в банке. Итог пассива не равен долгу.
- Число закупок/контрактов не доказывает успешное исполнение. Арбитражный агрегат не раскрывает предмет спора.

Справочник хранится в репозитории с version, источником (case/Q&A/проверенный reference) и тестовыми примерами. Модель может читать нужные фрагменты через внутренний lookup; vector search не обязателен. Юридические определения/пороги не добавлять без проверенного источника и даты.

## 7. RPC, assistant-stream и lifecycle

RPC-команды и публичное состояние определены в 10. Использовать штатный assistant-stream encoder/response и готовый assistant-ui transport runtime. Не собирать SSE вручную и не смешивать в одной реализации старый data-stream и SSE codecs. Выбор согласованной версии/codec — проверка V01 при реализации.

**Зафиксировано:** уход со страницы прекращает подписку, но не run. Явная команда cancel останавливает работу. Восстановление UI сначала получает сохранённую публичную проекцию, затем подписывается на активный run. reconnect не запускает повторно исходное сообщение.

По документации assistant-stream обычный `create_run` callback может отменяться при закрытии response. Поэтому агентный task не привязывается к lifecycle response: callback доставки подписывается на уже управляемую задачу. Точную интеграцию проверить на выбранной версии, использовать готовые средства библиотеки там, где они покрывают это поведение. Это локальная задача реализации, не повод менять стек. [Assistant Transport](https://www.assistant-ui.com/docs/runtimes/custom/assistant-transport)

Один активный run на thread. Follow-up во время работы инструмента принимается немедленно в persistent inbox; на следующей безопасной границе до обращения к модели новые сообщения добавляются в checkpoint state и помечаются applied. Это не второй параллельный graph run. request ID гарантирует отсутствие дубликатов. Подробная семантика — дополнение 1.1 ниже.

MVP один процесс-владелец активных задач. Память процесса может хранить task handles и подписчиков; единственная копия истории и результата там не хранится. При shutdown — ограниченное graceful завершение, checkpoints и interrupted status. После падения задачи не объявляются автоматически продолжающимися. Продолжение с checkpoint — явное действие, без обещания exactly-once для повторяемых инструментов.

## 8. Публичное состояние и артефакты

В UI публикуются message blocks, безопасные activity labels, вопросы, refs, идентификаторы/версии артефактов и статус run. Не публиковать внутренний prompt, сырые tool arguments/results целиком, секреты, скрытую память и chain-of-thought. Достаточная наблюдаемость: «Читаю условия поставки» → «Уточняю дату комплектации» → найденный факт и источник.

AI-вывод содержит: вопрос, краткую рекомендацию, основания, неизвестное, условия/следующие действия, confidence limitations, refs и версии данных. Поле уверенности описывает границы данных словами; не генерировать псевдоточный процент надёжности.

Пользовательское решение никогда не записывается вызовом save_analysis_artifact. После нового документа старое решение сохраняется, AI-черновик может обновиться; UI предлагает пересмотр. Историческая рекомендация остаётся привязанной к старой context_version.

## 9. Сквозной сценарий приёмки

Учебная Компания А, финансовые значения из предоставленного отчёта ИНН 7449088645; не актуальная оценка реального бизнеса. Сделка/документы синтетические.

1. Пользователь рассматривает поставку за 2,4 млн ₽; агент выясняет аванс 80%, срок 3 недели, задержка останавливает монтаж.
2. Domain-функция считает 1,92 млн ₽ аванса. MCP даёт финансовые периоды: выручка 2025 — 74,586 млн, капитал −300 тыс.; годом ранее −1,224 млн. Агент не говорит о безусловном ухудшении капитала, хотя он остаётся отрицательным.
3. Агент спрашивает о наличии товара, потому что срок критичен. В КП: «21 день после комплектации», без даты комплектации. Это не подтверждает срок отгрузки через три недели от аванса.
4. Пользователь записывает «Готов при условиях»: подтверждение наличия и определённый срок.
5. После возвращения добавляет складскую справку на другое юрлицо. Агент сопоставляет реквизиты, не выдумывает аффилированность и не обвиняет в мошенничестве; спрашивает о стороне договора и основании поставки.
6. Пользователь откладывает аванс до уточнения. Новый AI-вывод и новое решение сохраняются отдельно от предыдущих.
7. Дополнительно Компания Б: цена 2,6 млн, аванс 20% = 520 тыс. Разница авансов 1,4 млн при разнице цены 200 тыс. Это факт о предложениях, не доказательство безопасности Б. Сравнение пяти компаний доступно в том же проекте.

Проверить также короткий ответ по одной строке без tools, отсутствие финансов, неоднозначное название, покупателя с отсрочкой и документ с вредоносными инструкциями. Источники должны быть разрешимы, обновление контекста наблюдаемо, финальный результат отвечает вопросу пользователя.

## 10. Сессии, вложения артефактов и skills — версия 1.1

У каждой рабочей сессии свой thread_id, история и checkpoints. Проект общий, чаты изолированы по истории. При открытии нового чата передать цель и подтверждённые условия проекта, список материалов и явно прикреплённые артефакты, но не все предыдущие разговоры. Артефакт в сообщении привязан к версии/разделу и трактуется как предыдущий анализ, не первичный факт.

Работа с пользовательскими документами проходит через skills. Использовать штатную загрузку Deep Agents по Agent Skills specification: каталог metadata → выбор → чтение инструкции → разрешённые операции → результат. Готовые источники MarkItDown и PDF выбраны в 11; не писать собственную систему discovery. Фактический runtime skill invocation создаёт trace «Использую навык …» с версиями, входными/выходными refs и статусом. Навык сам по себе не даёт полномочия на shell/network: enforcement в наших adapters.

Базовые сведения reports по-прежнему доступны через MCP. Продуктовые правила проверки — доменные инструкции harness; не нужно оборачивать любой ответ на приветствие в фиктивный skill. Для XLSX skill читает нужные листы/диапазоны и сопоставляет предложения, для DOCX — условия, реквизиты и противоречия, сохраняя локаторы источника. Для простого текстового документа достаточно готового conversion skill и scoped reader.

## 11. Follow-up во время инструмента

1. UI отправляет отдельный запрос follow-up, не ждёт закрытия текущего streaming request. Сервер проверяет thread/project и сразу сохраняет command+message ID, возвращает accepted/queued.
2. Текущий инструмент продолжает работу; новое сообщение не может изменить уже отправленные ему аргументы. Нельзя писать конкурентно в graph state из HTTP-handler.
3. Перед следующим обращением к модели runner через поддерживаемый hook/middleware забирает новые команды по sequence, добавляет сообщения и вложения в контекст и checkpoint. UI получает applied: «Уточнение учтено».
4. Если следующее сообщение изменило цель/сумму, результат завершившегося инструмента остаётся фактом; агент переоценивает его значимость и не продолжает старый план автоматически.
5. Перед фиксацией окончательного ответа снова проверить inbox. Если follow-up пришёл во время генерации ответа, уже показанный текст не стирать: пометить как ответ до уточнения и выполнить следующий turn. Если предыдущий run успел завершиться, создать следующий run той же сессии атомарно.
6. Explicit cancel отменяет run; queued сообщения не исполняются молча после отмены, остаются доступными для явного продолжения. Очередь и статусы переживают reconnect. Retry с тем же ID не дублирует очередь.

Готовые middleware/checkpointer используем там, где есть нужные точки расширения; небольшой inbox adapter связывает прикладные команды с ними. Native semantics конкретной версии проверяются V09, а не предполагаются. Не реализовывать управление исполнением через стороннюю модификацию checkpoint SQL.
