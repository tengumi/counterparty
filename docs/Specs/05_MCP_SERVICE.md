# 05. MCP-сервис данных контрагентов

Версия 1.1 · 05.09.2026. [Индекс](00_OVERVIEW_AND_INDEX.md) · [Контракты](10_SYSTEM_CONTRACTS.md).

## 1. Назначение

Отдельный FastMCP-сервис предоставляет агенту понятные, ограниченные операции чтения отчётов. Источник — схема `reports`, заполненная данными заказчика. UI Backend получает свои сводки из тех же сущностей и shared domain functions. MCP не управляет проектами, памятью и документами клиента.

Использовать FastMCP HTTP transport / Streamable HTTP на `/mcp`. Штатная сериализация, lifecycle и схема tools — средствами библиотеки. Stateless HTTP transport допустим и предпочтителен для наших независимых чтений; состояние диалога не хранится в MCP-сессии. Актуальные параметры закрепить после smoke test. [FastMCP HTTP](https://gofastmcp.com/deployment/http)

## 2. Набор инструментов

| Tool | Когда вызывать | Вход | Выход |
|---|---|---|---|
| get_company_overview | Идентифицировать компанию, выбрать значимые разделы | Ровно один inn или report_id | Идентичность, snapshot metadata, компактные факты, available_sections, warnings, refs |
| get_report_section | Проверить конкретный аспект, получить подтверждение | report_id, section enum, фильтры, cursor, limit | Типизированные записи/факты, availability, pagination, source refs |
| compare_companies | Сопоставить кандидатов без ручного объединения цифр | 2–20 report_ids, список критериев, year_policy | Строки по компаниям, значения, периоды, неполнота, refs, warnings |

ИНН разрешается только среди импортированных компаний. При выборе по inn overview возвращает последний доступный snapshot и его report_id; последующие вызовы агента используют закреплённый report_id. Вызов с неизвестным ИНН возвращает not_found, не инициирует внешний поиск.

Разделы: profile, status, financials, activities, proceedings, arbitration, procurement, licenses, inspections, founders, related_entities, contacts, tax_systems, risk_signals, coefficients, branches. Возвращается только разрешённая политикой проекция. Общий инструмент с enum разделов предпочтительнее десятков узких tools.

Фильтры типизированные, например active для proceedings, years для financials/arbitration, role/status для судебных агрегатов. Запретить свободный SQL, произвольные имена колонок и URL. Defaults: limit=20, max=100 записей; размер ответа ограничить, продолжение обозначить next_cursor и truncated. При большом тексте возвращать компактные записи и возможность уточнить, не резать JSON посередине.

## 3. Agent-friendly контракт

Описание каждого tool должно отвечать: когда использовать, когда не использовать, необходимые параметры, единицы/периоды, возможные ошибки, способ получить продолжение. Добавить 1–2 коротких примера корректного вызова. Tool schema строится из Pydantic, ответы — структурированный JSON, не Markdown-отчёт внутри строки.

Каждый факт содержит источник и смысловую метку. Если section missing — это видно отдельно от present_empty. Ответ «рисков нет» недопустим как замена пустому результату. Полные имена компаний не повторять в каждой строке большого раздела; общий company/report metadata вынести в envelope.

Сравнение возвращает факты и расчёты, но не модельный ranking. Цель сделки передаётся агенту из workspace и влияет на выбор criteria. Условия пользовательских предложений не отправляются в этот MCP автоматически: инструмент читает reports и не имеет workspace-доступа. Полное сравнение «факты + КП» собирается агентом/продуктовым backend из двух источников.

## 4. Аутентификация и права

Внутренний сервис вызывается Agent Service по server-side credentials. DB-роль MCP — SELECT только нужных relations схемы reports, без workspace. Транзакция не получает права записи даже если tool ошибочно попытается изменить данные. Объявления readOnlyHint — дополнительные metadata, не механизм enforcement.

Лимиты, авторизация и проверки report_ids выполняются сервером. Модель не выбирает tenant или получает секретные токены. Таймауты, ограниченный параллелизм и безопасные ошибки; логировать tool name, latency, статус и объём, но не весь отчёт по умолчанию.

## 5. Внешний MCP как опциональная ветка

Наличие внутреннего MCP не означает публичного endpoint для любого AI. Внешний доступ требует отдельного deployment/policy, client identity и whitelist полей. OAuth инициируется пользователем, доступ read-only, ограничен scope и сроком, может быть отозван. Только разрешённая версия отчётных данных, без внутренних банковских сведений и пользовательских файлов по умолчанию.

Mock OAuth в демо подписывается как демонстрационный и не считается реализованной защитой. На внешнем endpoint нельзя показывать mock-экран согласия и при этом выдавать реальные закрытые данные. Отзыв должен прекращать новые обращения; уже переданные внешнему клиенту сведения нельзя обещать удалить со стороны банка.

Юридическая допустимость внешней передачи и условия источников не подтверждены. Основное демо полностью работает со внутренним MCP. Не заявлять снижение банковского AI-инференса как доказанный эффект: внешний клиент может оплачивать свою модель, но расходы на данные/MCP/обслуживание остаются.

## 6. Приёмка

- Все три tools доступны штатному MCP-клиенту и LangChain-адаптеру; ручной MCP-протокол не реализован.
- По report_id UI и MCP возвращают согласованные суммы/периоды.
- 100+ записей раздела выдаются постранично; omitted и truncated различимы.
- Неизвестный ИНН, отсутствующий раздел, invalid filter и timeout имеют отдельные исходы.
- MCP не читает workspace и не изменяет reports.
- Сравнение пяти компаний работает при неполных данных одной из них.

Пакет интеграции LangChain с MCP выбирается из штатной экосистемы; работа соединений и async cleanup проверяется при реализации. Окончательный контракт tools — [10_SYSTEM_CONTRACTS.md](10_SYSTEM_CONTRACTS.md).
