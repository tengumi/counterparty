# 08. Разработка, проверки и критерии готовности

Версия 1.1 · 05.09.2026. [Индекс](00_OVERVIEW_AND_INDEX.md).

## 1. Правила реализации

Python 3.13, asyncio, FastAPI, Dishka, Pydantic, LangChain/LangGraph/Deep Agents. SQLAlchemy async, psycopg 3, Alembic. Frontend: React/TypeScript/Vite, assistant-ui, Core DS. Использовать штатные инструменты фреймворков, типизированные адаптеры на границах и переиспользуемые компоненты. Не писать свой agent loop, checkpoint engine, MCP protocol, chat runtime или streaming codec.

Закрепить совместимые версии uv.lock и frontend lockfile. SDK с preview/unstable API допускается только в узком адаптере с проверкой поведения; не размазывать зависимость по всему приложению. Версии сверяются при реализации; этот документ не выдаёт непроверенную матрицу совместимости за факт.

## 2. Асинхронность и lifecycle

- Все сетевые и DB-вызовы в async request path — через async APIs.
- DB pools, HTTPX AsyncClient, MCP client и model clients создаются в lifespan/composition root, переиспользуются и закрываются корректно.
- Dishka: application scope для pools/clients, scope операции для session/UoW. Для долгого run зависимости должны жить независимо от короткого HTTP-request scope.
- Не делить один AsyncSession между параллельными tasks. Не держать транзакцию, пока LLM генерирует или инструмент ждёт сеть.
- Синхронный PDF/OCR/library code выносить через bounded offload; тяжёлый CPU — отдельный процесс при необходимости. Синхронный CLI миграций вне event loop допустим.
- Ограничить concurrency инструментов, timeout каждого внешнего запроса, длительность и стоимость run. CancelledError не подавлять как успешный ответ; cleanup в finally.
- Фоновая работа управляется приложением, task handles удерживаются до завершения, исключения наблюдаемы. Не использовать «забытый» create_task без владельца/обработки ошибок.
- Запуск агента отделён от assistant-stream подписчика. Отмена подписки при уходе не равна cancel run.
- При одиночном процессе не обещать горизонтальную масштабируемость runtime registry. Перед добавлением replicas нужен общий run ownership/queue и механизм доставки событий.

## 3. Код и качество

`ruff check`, `ruff format`, Google convention для docstrings и согласованный набор lint rules. Ruff formatter — отдельное правило форматирования; не называть его реализацией всего Google Style Guide. `mypy --strict`: типы прикладных сервисов, репозиториев, DTO и async iterators. Для недостаточно типизированных внешних библиотек — локальные Protocol/adapter/stubs; не отключать проверки глобально.

pytest + async plugin для meaningful tests. Frontend: tsc strict, lint, production build; браузерный тест сквозной интеграции. Pydantic DTO не равны ORM models. Миграции не запускаются каждым web worker при старте; отдельный шаг deployment. Fixture секретов нет в git. Логгирование структурированное, без полного текста документов по умолчанию.

## 4. Что проверяем при реализации без повторного обсуждения архитектуры

| ID | Проверка | Условие успеха | Если не выполнено |
|---|---|---|---|
| V01 | assistant-stream ↔ assistant-ui | Совпадающий codec, текст/действия/состояние/ошибка, типизированный converter | Настроить документированный адаптер и закрепить версии; не менять стек молча |
| V02 | Закрытие страницы | Run продолжается; возврат показывает текущее или итоговое состояние без повторного запуска | Развязать task и delivery callback; проверить штатные resume hooks |
| V03 | Явная отмена | Работа прекращается, partial state сохранён, terminal status корректен | Исправить отмену и cleanup |
| V04 | Persistence и restart | Тот же thread после restart; прерванный run явно отмечен, можно продолжить | Проверить saver, migration/schema placement и recovery procedure |
| V05 | MCP integration | Три tools вызываются асинхронно, ошибки/таймауты/пагинация обработаны | Использовать штатный адаптер нужной версии |
| V06 | Core DS + assistant-ui | Ввод, attachments, фокус, кнопки и ссылки работают без двух конфликтующих состояний | Hook-based composition вместо несовместимого wrapper |
| V07 | JSON importer | Сохранены реальные значения, периоды, unknown и $numberLong | Исправить parser mapping, не подменять данные |
| V08 | Documents | PDF + PNG/JPEG/TXT + DOCX/XLSX/текстовые форматы через skills, provenance, ошибки, лимиты | Выбрать OCR/vision adapter; неподдержанное чтение показывать честно |

Проверки V01–V13 — работа delivery, не список вопросов пользователю. Самостоятельная реализация доступна до их завершения; готовность MVP требует прохождения.

## 5. Тесты, которые имеют значение

**Данные/расчёты:** идемпотентный импорт; 100 снимков; деньги-строки и Extended JSON; missing против zero; отрицательный/нулевой знаменатель; несопоставимые годы; арбитражные агрегаты без двойного счёта; 1,92 млн против 520 тыс. аванса; изоляция источников.

**Приложение:** доступ к чужому project/document/thread запрещён; повтор запроса не создаёт дубликат; одна активная задача на thread при доступном persistent inbox для follow-up; новое условие помечает старый вывод outdated; агент не может записать пользовательское решение; удаление проекта очищает принадлежащую ему память.

**Интеграция:** MCP + PostgreSQL на реальной структуре fixture; assistant-stream + assistant-ui; reconnect/cancel/error/terminal state; документы и источник в панели; сравнительная таблица пяти компаний.

**Агентные evals:** ручные живые прогоны (решение пользователя 06.09.2026): сценарий аванса и неопределённой комплектации; справка другого юрлица; покупатель с отсрочкой; отсутствующие финансы; ОКВЭД с misleading исходным пояснением; агрегированный суд без текста; вредоносная инструкция в документе; простой вопрос без лишних tools. Оценивать действия, релевантность вопросов, факты и refs вручную. Не писать и не восстанавливать хрупкие автотесты конкретных ответов, промптов, форматирования, выбора заметок и сценарных действий модели, включая scripted/deterministic модели. Общие устойчивые тесты контрактов, инфраструктуры, изоляции, evidence refs и безопасности сохраняются.

Deterministic mocks используются для воспроизводимых API/UI тестов. Отдельный небольшой набор реальных LLM-прогонов фиксирует model/version/prompts и подтверждает поведение агента. Не выдавать scripted chat за работающего агента. Mock данные в демонстрации помечены.

## 6. Метрики и наблюдаемость

Пользовательский результат: ответил ли агент на вопрос, есть ли основания и конкретное следующее действие; время до полезного вывода; число повторных/ненужных уточнений; доля источников, открывающихся в нужное место. Для демо экспертная оценка по рубрике, не выдуманная статистика пользователей.

События продукта: project_created, first_message_sent, report_opened, comparison_opened, question_answered, document_uploaded, evidence_opened, analysis_completed, decision_saved, project_reopened. Отдельно run duration, first visible activity, first token, tool latency, errors, model usage, cost estimate и context size.

Retention сервиса: возвращения к проверкам и новые повторные проверки; retention подписки: продления/отток с контрольной группой; банковская активность: возможное увеличение доли операций в Альфе. Все три — будущие причинные гипотезы, их нельзя доказать кликабельным демо или несколькими runs. В MVP нет банковских данных для последней метрики.

Экономика: встроенная модель оплачивается оператором решения; стоимость на завершённую проверку, p50/p95 token usage, расходы на OCR/tools/storage. Отдельная монетизация агента не предполагается. Не заявлять окупаемость без базовых затрат и эффекта удержания. Можно логировать estimates по настроенной цене провайдера, с датой тарифа.

## 7. Этапы разработки

| Этап | Результат | Минимальный gate |
|---|---|---|
| 1. Контракт и вертикальный каркас | Импорт одной реальной записи, saved project, stub stream, Core DS composer | request ID, project scope, event/state rendering |
| 2. Данные и детерминированный слой | Импорт всех 100, overview, sections, evidence, сравнение | V07 и числовые тесты |
| 3. MCP и агент | Три tools, знания Q&A, контекст и вопросы | V05 + реальный агентный прогон |
| 4. Документы и память | Источник из КП, новые условия, версия вывода, повторный визит | V04/V08/V11/V12/V13, сценарий справки другого юрлица |
| 5. UI и lifecycle | Два экрана, панели, решение, reconnect/cancel, сравнение пяти | V01/V02/V03/V06/V09/V10 |
| 6. Финальная приёмка | Экспертные evals, ограничения, демо и замеры | Все обязательные AC пройдены |

Frontend и backend могут работать параллельно по контрактам после этапа 1; это не требование закончить весь backend до UI. Дизайнер использует 07 сразу. Сроки назначает команда относительно даты финала, здесь не создаётся выдуманный календарь.

## 9. Definition of Done

Работает основной сценарий F01–F09 и дополнительное сравнение пяти компаний; есть дизайн масштабирования до 20; ссылки разрешаются; история/контекст восстанавливаются; решение человека отделено от AI; закрытие вкладки не отменяет работу; выбранные исходные поля не искажены; цены/лицензии/скоринги не выдуманы; ошибки и лимиты видны; тесты и реальные агентные evals пройдены. Остаточные ограничения перечислены явно. Внешний MCP не является обязательным условием завершения основного MVP.

## 10. Обязательная приёмка дополнения 1.1

- V09 Follow-up: отправить сообщение во время намеренно долгого инструмента; получить accepted до его завершения, затем applied до следующего model call; убедиться, что новая сумма влияет на ответ. Проверить дубль запроса, cancel, гонку завершения, reconnect и порядок двух уточнений.
- V10 Сессии: два чата одного проекта, независимая история, общий подтверждённый контекст. Переключение не отменяет run и не переносит черновики/queued сообщения в чужой thread.
- V11 Артефакты: прикрепить конкретную версию из другого чата; новая версия не подменяет её; отсутствующая/чужая ссылка корректно отклоняется.
- V12 Skills: выбранный навык действительно загружается штатным механизмом; trace содержит skill ID/version и реальные input/output refs. Документная операция не обходит skill executor; навыки не расширяют filesystem/network permissions.
- V13 Документы/GIL: XLSX с несколькими листами, формулами, пустотами и скрытыми строками; DOCX с таблицей и условиями; текстовые форматы. Проверить provenance. Во время parsing запрос health и stream UI остаются отзывчивыми. Для выбранного native участка проверить release GIL и thread safety; не делать вывод по слову Rust/C++.

Рекомендуемые execution policies: native reader с подтверждённым GIL release — bounded thread pool; Python-heavy conversion и непотокобезопасный PDF — process fallback. Один thread не способен принудительно остановить произвольную зависшую native-функцию: для жёсткого timeout необходим worker process. Это локальная техника обработки документов, не новая микросервисная платформа.
