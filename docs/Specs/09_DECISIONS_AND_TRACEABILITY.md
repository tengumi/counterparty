# 09. Принятые решения, полнота и открытые вопросы

Версия 1.1 · 05.09.2026. [Индекс](00_OVERVIEW_AND_INDEX.md).

## 1. Что считается принятым

Исходная архитектура пользователя сохранена: PostgreSQL с двумя областями, отдельный MCP, stateless сервис агента с восстановлением контекста, UI Backend с CRUD и детерминированным слоем, отдельные REST/RPC маршруты. После обсуждения выбран assistant-stream и assistant-ui. Готовый Agent Server не является обязательным. Фоновая работа после закрытия страницы обязательна; её wiring проверяется при реализации.

Названия таблиц/DTO/endpoints, лимиты tool calls и timeout в новых документах — предложенные defaults ТЗ. Они не представлены как дословные требования заказчика. Утверждение, что весь стек проверен в работе, отсутствует: это задача delivery.

## 3. Что изменено в прежнем дизайн-ТЗ

Переиспользован DESIGN_BRIEF_V2.md, а не создана другая экранная концепция. Сохранены R01–R10, S1/S2/P1/C1/D1, основные тексты, размеры, формы, данные, F01–F13, таблица Core DS и критерии приёмки. Добавлены R11–R14, F14–F16 и E09–E12 для фоновой работы/восстановления. Уточнено отображение таблицы на mobile. Фраза «не обещать продолжение server-side» заменена подтверждённым требованием. Ошибка отсутствующего отчёта уточнена: пользовательский документ не создаёт банковскую карточку автоматически.

Не менять содержимое старых файлов в обход версии: этот пакет — новое согласованное издание. Ссылки внутри пакета относительные для передачи архивом; дизайнерский документ содержит весь нужный ему контекст.

## 4. Вопросы, которые действительно требуют внешней информации

| Вопрос | Кому / когда | Что делаем до ответа |
|---|---|---|
| Какая модель, провайдер и доступный API будут в демо? | Команде до реальных LLM evals | Provider adapter и конфигурация; не хардкодить модель. В кейсе предпочтительны Qwen/GPT-OSS, но допускаются другие |
| Как точно отображать raw YELLOW/RED ЗСК при требовании green/grey? | Кейсодателю до финальной демонстрации этого поля | Neutral «Отображение требует уточнения», raw сохраняется |
| Разрешён ли внешний MCP/export и какие поля? | Кейсодателю/ИБ при включении внешней ветки | Основной MVP только внутренний MCP, внешние fixtures синтетические |

Уточнение провайдера не блокирует подготовку ТЗ. Остальные вопросы не нужно перекладывать на пользователя каждый раз: schema placement, codec, OCR adapter, версия React, подключение resume hooks — инженерные проверки V01–V08.

## 6. Итог самопроверки

Документальная проверка набора: полнота требований из переписки, ссылки внутри пакета, актуальные source paths JSON, согласованность имен DTO/endpoints и отсутствие возврата к comparison-first UX. Проверка не равна запуску приложения: приложение в этой задаче не разрабатывалось. Реальная приёмка — по 08 после реализации.


Результат автоматизированной документальной проверки: 11 Markdown-документов, все локальные ссылки разрешаются, code fences парные. Из прежнего дизайн-ТЗ сохранены все 67 уникальных ID экранных элементов/сценариев; в новой версии 78 ID с учётом добавлений. 244 из 252 исходных строк сохранены без изменения. Дополнительно сверены реальные пути finReports, ключи pf/pa/pp/df/da/dp арбитража, branchesInfo, registrationInfo и status.reasonName. Миграции, API и реальные UI здесь не запускались — это пакет ТЗ.


## 7. Изменения 1.1 по новой обратной связи

Сняты прежние ограничения «один чат на проект» и «нельзя отправить сообщение во время run». Добавлены threads, artifact attachments, persistent pending commands, skill invocations, локаторы XLSX/DOCX и видимые сессии. Готовые skills указаны с конкретными upstream источниками в 11. Старое дизайн-ТЗ переиспользовано: новые элементы S2-13…S2-19, P1-09…P1-11 и F17…F21 добавлены к существующим, прежние ID не удалены.

Ранний результат самопроверки выше относится к версии 1.0 (11 документов). Версия 1.1 содержит 12 документов; её проверка дополнительно ищет оставшиеся запреты нескольких чатов/follow-up, согласует новые endpoints и сохраняет все прежние ID.

Критерии поведения агента остаются первыми: замечает значимое, уточняет, использует новый контекст и помогает решить задачу. Усиление модели — отдельный конфиг/eval, не повод усложнять UI. Предложенные кейсодателем названия DeepSeek v4 flash / GLM 5.3 flash записываются как кандидаты из комментария, а не как подтверждённые доступные model IDs; API уточнить при интеграции.
