# Архитектура локального MVP

Фактическая реализация на 05.09.2026. Постановка и Q&A — в
[индексе материалов](../artifacts/INDEX.md); продуктовые гипотезы и направления
команды — в [продуктовом пакете](README.md). Статус работ — в
[solution_status.md](solution_status.md).

## Границы и стек

Основной workflow — явный LangGraph. Python выполняет поиск, расчёты, сравнение
и проверку источников. LLM понимает запрос, извлекает условия пользователя,
выбирает следующий шаг проверки и формулирует ответ по доступным основаниям.

Python 3.12 + uv; FastAPI/Uvicorn; Pydantic; RapidFuzz; Decimal;
LangGraph + SQLite checkpointer; совместимый Chat Completions через официальный SDK.
React/TypeScript/Vite, базовые Alfa Core Components и Recharts — интерфейс.
Ключ берётся только из `COUNTERPARTY_LLM_API_KEY`, адрес и модель задаются окружением.
Название провайдера не используется как бренд продукта.

Backend раздаёт готовую сборку из `src/counterparty_agent/ui/build`.
Единый запуск — `uv run python src/main.py`; изменения UI собираются из `frontend/src`.
Импорты ведут к реализации, без файлов-переэкспортов. Deep Agents, vector DB,
внешний поиск, база отчётов и MCP в runtime не подключены.

## Данные и детерминированная аналитика

`data/` читает вложенный JSON, распаковывает Mongo Extended JSON, сохраняет
raw enum, aliases, source/record hashes и пути. CSV зарезервирован, но отдельного
рабочего адаптера нет. Исходные отчёты остаются локальными и не коммитятся.
Денежные значения — Decimal; пропуски не становятся нулями.

`query.py`: извлечение → формат/контрольная сумма → exact ИНН/ОГРН →
нормализованное название → RapidFuzz top-3 → подтверждение неоднозначности.
Модель не подтверждает кандидата вместо пользователя. Подбор похожих групп отложен.

`analytics/` строит проверенные выводы и матрицу. `validate_analysis` и
`validate_comparison` повторяют правила и проверяют значения, порядок, даты и evidence.
Общий финансовый год выбирается кодом. При отсутствии общего года сохраняется
один явный период с пропусками. Денежные значения выгрузки считаются рублями без
дополнительного множителя: `60746000` означает `60 746 000 ₽`. Денежное ранжирование
всё равно не выполняется без отдельной утверждённой методики; различия значений
не объявляются ростом бизнеса без подтверждённой сопоставимости.

`zskRiskLevel` переносится без изменения; `baseInfo.riskLevel` остаётся отдельным полем.
Серый, отсутствующий и нераспознанный сигнал различаются. На вопрос о причине цвета
доступен отдельный факт «Причина этой оценки в отчёте не указана»; если оценки нет,
это указывается прямо. Другие сигналы не объявляются причиной цвета.
Отсутствие данных и отсутствие обнаруженного сигнала не означают отсутствия риска.

Даты в тексте ответа и интерфейсе показываются по Москве. Исходные временные метки
и расчётная дата анализа сохраняются в UTC; отображение не меняет момент проверки.

## Вход запроса и два режима ответа

```text
восстановление сессии → намерение и условия → поиск/подтверждение
    → загрузка → расчёты → проверка
        ├→ карточка/матрица
        ├→ вопрос о показателе → выбор готовых фактов → проверка ответа
        └→ аналитический вопрос → цикл проверки под цель → синтез → проверка ответа
```

`ai/router.py` возвращает разрешённое действие: `lookup`, `compare`,
`add_to_comparison`, `ask`, `show`, `clarify` или `unsupported`.
В плане также есть режим ответа, дословные новые условия сделки и `review_topics`:
до шести разных разделов первоначального чтения. Список ограничен серверной схемой,
не содержит фактов, не разрешает внешние инструменты и не сохраняется в checkpoint.
Роутер видит вопрос, реквизиты и названия текущего выбора, исходные номера группы,
фокус, последние темы и условия. Полные отчёты, документы и архив переписки
ему не передаются.

JSON проверяется Pydantic; адресаты и условия должны происходить из сообщения.
JSON mode не гарантирует соответствия схеме, поэтому нужна серверная проверка
([документация API](https://developers.openai.com/api/docs/guides/structured-outputs#json-mode)).
`workflow/semantic.py` дополнительно проверяет полноту явных реквизитов/названий,
организационные формы, номер участника и допустимые действия.
Новая неизвестная компания не заменяется предыдущей карточкой.

Точный реквизит, список ИНН/ОГРН, переоткрытие и кнопки обходят LLM-роутер.
После поиска может запуститься аналитический сценарий, если для него уже есть условия.
При первом открытии без цели помощник предлагает уточнить задачу либо выбрать общую
проверку. Восстановление страницы повторно не запускает модель.
Ошибка условия не отменяет остальные дословные поля и корректный адресат: после попытки
исправления сохраняются только прошедшие проверку части плана. При отказе/уточнении
роутера код может восстановить явную просьбу проверить один ИНН/ОГРН. Проверка совпадения
названия сохраняется; отрицания, гипотезы, документы и изменения группы не обходятся.
Иначе ошибка сохраняет выбор; непонятый вопрос не используется как имя компании.

Узкие вопросы используют `ai/catalog.py`, `comparison_catalog.py` и `selector.py`.
Модель выбирает до восьми ID готовых фактов; сервер собирает их неизменяемый текст
и проверяет ссылки, адресата и доступный период. При ошибке допускается исправление,
затем возвращается отказ с сохранением карточки. Для больших групп этот режим
передаёт компактные темы, а код разворачивает значения всех участников.

Короткий вопрос о предыдущем годе разрешается только по однозначной прошлой теме.
Квартал не подменяется годом; групповые финансы остаются в периоде текущей матрицы.
После аналитического ответа сохраняются исходные ID фактов; для группы темы
сопоставляются существующим фактам сравнения без добавления новых годов.
Сложный анализ за относительный период требует явного уточнения и не подменяется
анализом всех доступных лет.

## Цель, условия и аналитический цикл

`ai/deal.py` хранит цель, роль контрагента, предмет, сумму, условия оплаты и срок.
Каждое условие — дословное сведение пользователя с собственным evidence, временем
и ревизией контекста. Новое значение заменяет прежнее в текущей проверке.
Общая проверка включается явно; помощник не превращает уточнения в обязательную анкету.
Роль контрагента отличаем от роли пользователя: «для нас как продавца» не меняет
покупателя на поставщика. «Оплата через 60 дней» — условие оплаты, не срок исполнения.
Последствия оплаты строятся с учётом направления: отсрочка покупателю означает ожидание
платежа после передачи товара, аванс подрядчику — перечисление до выполнения работ.
Это описание условий, а не прогноз платёжеспособности. Неясное направление обозначается
явно; одна величина прибыли/убытка не превращается в решение о предоставлении отсрочки.
Явное условие оплаты уже позволяет начать анализ без повторного общего вопроса
«зачем проверяете». Неизвестная роль при этом не угадывается; уточнить её можно отдельно.

`workflow/review.py` — отдельный ограниченный LangGraph:
`start → read/decide → read → decide/finish`, с выходом в один уточняющий вопрос
либо итоговый ответ. `start` проверяет первоначальные разделы из роутера и их
доступность после разрешения адресата; при пустом плане сохраняется прежний цикл.
Для одной компании без документов, обрезки контекста и непрочитанных разделов
с сигналами внимания первоначальное чтение ведёт сразу к синтезу и верификации.
Финансы также читают ограничения данных; вопрос по договору требует чтения документа,
а по оценке — статуса компании. Группа/фокус, документы и новые обстоятельства
сохраняют решение модели по прочитанным фактам. Проверки ответа не сокращаются.
Переключатель `COUNTERPARTY_LLM_COMBINED_PLANNING=false` отключает повторное
использование разделов роутера; это контроль задержек, а не отключение анализа.
За запуск допускается до четырёх решений о следующем шаге; за проверку — до двух
уточнений, включая начальный вопрос о цели. Уже известное или ранее спрошенное
поле нельзя запросить заново. Модель выбирает неизвестное поле, а пользователю
показывается нейтральный серверный вопрос: произвольный текст модели не переносится
в уточнение. Набор разделов зависит от цели и прочитанных фактов,
а не от фиксированной последовательности трёх чтений.

Адресат передаётся планировщику, синтезу и проверяющему как `review_scope`: выбранная
компания, её исходный номер и размер группы. При фокусе на втором участнике модель
получает именно его отчёт, а не ищет «вторую компанию» среди переданных фактов заново.
Пробел в отдельной теме нельзя объявлять отсутствием всего выбранного отчёта.
Эти метаданные учитываются вместе с фактами в лимите контекста и не добавляются в checkpoint.

Для аналитического цикла `COUNTERPARTY_LLM_REVIEW_MAX_TOKENS` задаёт предел каждого
ответа модели: 2400 по умолчанию, допустимо 500–8000; роутер и узкие вопросы
сохраняют свой бюджет. `COUNTERPARTY_LLM_REVIEW_TIMEOUT_SECONDS` ограничивает весь
цикл одним сроком: 120 секунд по умолчанию, допустимо 10–300, включая синтез,
верификацию и исправления. При превышении незавершённый ответ не показывается,
карточки и подтверждённые условия сохраняются; можно повторить или сузить запрос.
Этот срок не включает предшествующий роутер и не является лимитом всего HTTP-запроса.

Разделы ограничены статусом компании, финансами, судами, взысканиями, сигналами,
лицензиями, качеством данных и документами. Проверенные каталоги строит код.
Чтение возвращает относящиеся к теме факты; фиксируются фактически выполненные шаги.
Внутри одного приоритета финансовые периоды читаются от новых к старым; явно
запрошенный год идёт первым. Это не позволяет порядку годов в JSON вытеснять свежий
показатель при ограниченном контексте. Групповые факты не относятся к одной компании
только потому, что в их тексте встретился её ИНН.
Синтез получает ограниченную выборку. Если лимит контекста исчерпан, полнота
анализа явно не обещается: особенно для большой группы нельзя считать, что
в модель попали все факты каждого участника.

`ai/reasoning.py` формирует блоки «факт / вывод / что неизвестно / следующий шаг».
Формулировки и приоритеты выбирает LLM; копировать весь каталог не требуется.
Блоки ссылаются на конкретные факты. Код проверяет ID, числа в процитированных
основаниях и принадлежность источников. Отдельный вызов модели проверяет смысловую
обоснованность, актуальные условия и соответствие вопросу; неуспешный ответ
исправляется либо отклоняется. Наличие evidence и согласие второй проверки
не доказывают истинность интерпретации или исходного документа — нужны экспертные evals.
Проверяющая модель видит весь прочитанный каталог, а не только выбранные автором
цитаты: это позволяет заметить пропущенный ноль, другой год и противоречащий факт.
Ссылка на условие подсказывается при исправлении, но не добавляется автоматически.
Числовая проверка сохраняет знак; служебные короткие ID не попадают в текст интерфейса.
Для отрицательной прибыли код отдельно выводит модуль убытка с теми же источниками:
положительное число в этой формулировке не меняет знак исходной прибыли. Неуточнённый
показатель «прибыль» нельзя переименовать в чистую или операционную. Нулевая выручка
последнего доступного завершённого года и отрицательный капитал имеют явные границы:
это не доказательства прекращения работы или банкротства. Сводка взысканий показывает,
для скольких активных записей известна сумма; судебные требования и производства
нельзя просто сложить и назвать общим долгом.
При исправлении отдельных блоков сохраняются уже проверенные части; итог повторно
проверяется целиком. После повторной числовой ошибки частичная замена применяется только
к одному фактическому абзацу; весь результат затем проверяется по смыслу. Ошибочную
интерпретацию нельзя заменять одной цитатой, сохраняя зависимые от неё выводы.
Для составного группового вывода допускается до 32 оснований
на блок; это не отменяет ограничение входного контекста и проверку каждой ссылки.
Обычный черновик получает одну попытку исправления по конкретной ошибке; уже проверенные
блоки сохраняются. Затем `ai/briefing.py` формирует резервный ответ: актуальная оплата,
до трёх тем одной компании или двух тем каждого участника, ограничения и конкретные
действия. Отметки о судах/взысканиях объединяются с подробностями, финансовое расхождение
не вытесняет остальные обстоятельства. При историческом убытке сохраняется более поздняя
доступная прибыль. Порядок чтения разделов не меняет пользовательский порядок компаний.
Резерв учитывает сам вопрос: приоритет следующей проверки, границу полного долга,
прибыльность и банкротство нельзя заменять одной общей сводкой. При отсутствии сигналов
краткая проверка показывает это ограниченное наблюдение, последнюю выручку и отсутствие
данных о прибыли, а не только перечень пробелов. Убыток и отрицательный капитал
одного года сохраняются вместе как разные показатели.
Для малой группы код может подготовить сравнение числа активных производств: только
при единственном максимуме, не более шести участников и ограниченной длине текста.
Оно помогает выбрать, чьи взыскания уточнить сначала, но не ранжирует надёжность и не
назначает победителя. При равенстве максимумов приоритет по этому критерию не назначается.
В краткой сводке подробности заменяют дублирующую отметку той же темы; для вопроса
о пробелах выбираются разные темы и последний год, а не несколько одинаковых пропусков.
Подписи «Факт / Вывод» не добавляются к абзацам, тип и источники остаются в проверяемом
черновике. Это не новый скоринг и не доказательство полноты анализа.
Любой изменённый ответ, включая полную резервную сводку, проходит смысловую проверку
на соответствие вопросу; доверия по признаку «собрано кодом» нет. Вердикт повторно
используется только для неизменённого черновика. Просьба проверить финансовое состояние
и отрицание гарантии не считаются утверждением о платёжеспособности, но проверяются по смыслу.
Вопрос о достаточности цвета получает фактический сигнал и границу его применимости;
он не считается вопросом о пропусках. Причины цвета из других строк не выводятся.
Для вопроса по договору отдельный fallback обязан совместно
использовать цитату документа, актуальное условие и сведения отчёта. Непроверенный
текст модели пользователю не показывается.

`workflow/review_session.py` связывает этот цикл с основной проверкой.
Новые условия меняют контекст следующего анализа, но не исходные показатели
компании и не банковский цвет. Агент не рассчитывает собственный рейтинг,
не выполняет внешние действия и не одобряет сделку.

## Память и границы сессии

Checkpoint содержит ID компаний, кандидатов, ранее использованных фактов и фокуса,
source hash и служебные статусы. Полных отчётов, условий, вопросов и ответов в нём нет.
Цель и условия лежат отдельно в `browser_sessions.review_context` той же SQLite.
Они ограничены владельцем, сессией, источником и составом проверки.

Новая сессия или независимая компания не наследует прежнюю сделку.
Фокус внутри группы и добавление участников сохраняют её общий контекст.
Группа подтверждается целиком; дополнение применяется после разрешения всех позиций.
Неподтверждённый состав блокирует Q&A. Номера компаний относятся к серверному порядку,
а не к текущим фильтрам таблицы.

Смена источника сбрасывает прежний выбор. TTL и удаление сессии применяются также
к её условиям. Одновременно выполнять операции одной сессии нельзя; другая сессия
не блокируется ожиданием модели. Секреты, snapshots, PII и тела запросов не пишутся
в Git или логи.

## Сохранённый проект и документы

Проект необязателен для анализа. Он сохраняет состав/отбор, условия, открытые вопросы,
документы и версии резюме в `workspace_projects` существующей SQLite.
Фокус проектного чата хранится отдельно: следующий вопрос «у него» относится к выбранной
компании, явное обсуждение всей группы снимает фокус. Кнопка `set_focus` не вызывает LLM,
проверяет состав, владельца и ревизию. Изменение отбора убирает вышедший из него фокус.
Явное сохранение переносит условия выбранной сессии с проверкой владельца и scope.
Проект получает отдельную сессию; повторное открытие восстанавливает её или создаёт
новую после истечения прежней. Это не база карточек: отчёты по-прежнему читаются из JSON.

`projects/dialogue.py` использует общий роутер и аналитический цикл.
Команда «сопоставь условия договора» не превращается в название компании: до
роутера проверяются только явные реквизиты/названия, остальные адресаты — по его плану.
`projects/evidence.py` объединяет факты отчётов, условия и релевантные цитаты.
По вопросу и цели выбираются до 12 фрагментов из всех доступных документов,
без фиксированного выбора первых двух. При неполном чтении добавляется ограничение.
Слова «аванс» или «договор» не отключают доступ к фактам компании.

У вопроса есть ответ, статус, связь с условием и основания. Явный ответ в чате
или форме сохраняется как сообщение пользователя. Новое условие обновляет текущий
ответ; прикрепление документа само по себе вопрос не закрывает.
Поздний ответ также закрывает открытый вопрос по соответствующему полю. Вопросы,
показанные без модели, учитываются после её подключения. Если цель ещё ни разу
не спрашивали, общий первый вопрос работает и в основном чате, и в проекте.
`projects/review.py` предлагает резюме и diff по результату общего цикла.
Без модели доступен явно ограниченный просмотр фактов, без аналитического заключения.

Изменения проверяют owner и expected_revision. Изменение условий, состава,
документов или ответов отменяет предложение; принятое резюме остаётся с отметкой
`memo_stale`. Принятие сверяет proposal ID, ревизию, source hash, состав, hashes
документов и контекста. Старое или повторное подтверждение получает 409.
Метаданные источников сохраняются вместе с версией резюме.

TXT/MD UTF-8, PDF с текстовым слоем и DOCX: до 2 МБ, пяти файлов и 60 000 символов
на документ; PDF до 30 страниц без пароля. Парсер запускается отдельным процессом
без ключа модели, с лимитами времени и памяти; XML не разрешает внешние сущности.
Оригинальный файл не сохраняется, извлечённый текст остаётся локально. OCR и проверка
подлинности не реализованы. Документы считаются данными, инструкции из них не выполняются.

## Интерфейс и проверка результата

Главная страница начинается с поиска. После выбора компании или группы сводка
видна слева, а чат закреплён справа с отдельной прокруткой. Кнопка расширяет чат
и возвращает его сбоку без потери переписки и черновика. На узком экране доступны
переключатели отчёта и чата; подробности раскрываются внутри отчёта. Enter отправляет
вопрос, Shift+Enter переносит строку; подтверждение IME не отправляет сообщение.
Проекты, графики и матрица дополняют этот сценарий. Повторная отправка блокируется,
а устаревший ответ не заменяет новое состояние.

UI использует серверные значения. Decimal сохраняется в подписях, Number применяется
только для геометрии графиков. Пропуски — разрывы; незавершённые периоды не показываются
как полный год. Групповые агрегаты учитывают весь состав независимо от страниц таблицы.
Панель источников показывает компанию, происхождение, дату и ограничения.
React экранирует текст документов. Ответы с данными не кэшируются.

Автотесты проверяют переходы, изменение условий, фокус, периоды, evidence, документы,
owner/revision/hash и неподтверждённые ответы. Они не заменяют прогоны с текущей моделью
и экспертную оценку полезности. На 06.09.2026 контрольные живые сценарии основного
чата и проекта с документом прошли; актуальные времена и границы зафиксированы в
`DEMO.md`. Пользовательская оценка полезности и продуктовый эффект не доказаны.
Для публичного запуска нужны полноценная авторизация, квоты и политики хранения;
локальная cookie-изоляция их не заменяет.
