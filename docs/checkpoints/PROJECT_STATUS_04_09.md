# Описание проекта — промежуточная версия

**Проект:** рабочее пространство проверки контрагентов для Альфа‑Бизнеса  

## Краткая аннотация

Мы разрабатываем рабочее пространство для проверки и сравнения контрагентов в Альфа‑Бизнесе. Решение помогает предпринимателю или финансисту сопоставить несколько компаний по данным банковского отчёта, раскрыть основания каждого сигнала и понять, какие сведения значимы для конкретной цели проверки.

Основной отчёт и сравнение строятся детерминированно. AI используется для объяснения выбранных фактов и исследования неоднозначных сигналов. Агент появляется только внутри сохранённого проекта: он составляет план углублённой проверки, обращается к разрешённым данным и пользовательским документам, фиксирует неизвестное и предлагает обновление итогового артефакта проверки, умеет работать с пользовательскими файлами для уточнения деталей. В качестве дополнительного интерфейса рассматривается read-only MCP для подключения разрешённых данных Альфы к внешнему AI‑клиенту.

## Проблематика

Текущий сервис Альфа‑Банка уже собирает сведения о юридическом лице и рассчитывает риск, но результат предоставляется в виде отдельного отчёта. При проверке нескольких кандидатов пользователь вынужден последовательно изучать отчёты и самостоятельно сопоставлять финансовые показатели, судебные дела, исполнительные производства, реестровые признаки и другие сигналы.

Проблема состоит не только в объёме информации. Разные показатели отвечают на разные вопросы:

- банковский светофор отражает комплаенс‑риск, но не полностью описывает финансовую состоятельность;
- зелёный светофор может сочетаться с отрицательным капиталом или другой финансовой проблемой;
- наличие исполнительного производства само по себе не определяет критичность — важны сумма и масштаб компании;
- блокировка счёта ФНС является негативным фактором, но краткосрочная блокировка не обязательно означает невозможность работать;
- универсальных 3–5 главных сигналов нет: их значимость зависит от цели проверки.

Поэтому простой AI‑пересказ PDF не решает задачу полностью и легко воспроизводится во внешней языковой модели.

## Актуальная постановка задачи

Нужно сократить путь от списка известных кандидатов до обоснованного решения пользователя:

1. Принять один или несколько ИНН.
2. Построить единый сравнимый профиль компаний на основе доступных данных.
3. Раздельно показать комплаенс, финансовую устойчивость, судебно‑исполнительную нагрузку, опыт и полноту данных.
4. Дать пользователю сократить shortlist без автоматического выбора победителя.
5. Позволить раскрыть источник, дату и состояние любого существенного показателя.
6. Уточнить цель проверки и с помощью AI объяснить релевантные сигналы, ограничения и следующие действия.
7. В агентном сценарии сохранить план проверки, документы, открытые вопросы и итоговое решение.
8. Не выдумывать данные, не подменять банковский риск новым AI‑скорингом и не выдавать юридическое заключение.

Основной сценарий MVP — сравнение пяти поставщиков перед сделкой с последующим углублением по трём финалистам. Интерфейс проектируется с возможностью работы с 5–20 компаниями.

## Выбранное техническое решение

Решение разделено на независимые слои.

### 1. Детерминированный слой данных

- mock реального инфраструктурного слоя компании (json, csv -> бд), бекенд рабоет сразу с реальной бд
- единая схема dossier компании;
- воспроизводимые правила форматирования, сортировки и сравнения;
- отдельные состояния «события не обнаружены», «данных нет», «данные недоступны» и «данные устарели»;
- сохранение идентификатора evidence, источника и даты среза;

### 2. Web‑интерфейс

Планируется React‑интерфейс с использованием [Alfa Core Components](https://github.com/core-ds/core-components):

- таблица сравнения компаний;
- интерактивный отчёт;
- evidence drawer;
- связанная панель AI‑чата;
- сохранённый проект проверки;
- план агента, документы и decision memo.
- в качестве референса UI/UX берем ChatGPT Work / Claude Cowork (добавляя только нужный набор фич под комфортный разговор о потенциальном взаимодействии с поставщиком + организация в проекты или другую сущность - например, сделки)

### 3. AI‑слой

LLM получает не весь интерфейс в виде текста, а структурированный контекст и выбранные evidence‑элементы. Ответ должен:

- ссылаться на доступные входные данные;
- отделять факты от интерпретации;
- явно указывать неизвестное;
- учитывать цель проверки;
- не изменять значения банковских индикаторов.

Для единичного объяснения используется обычный запрос к LLM. 
Агентный режим применяется только для многошаговой работы с сохранённым состоянием, несколькими разделами и документами и позволяет комплексно обсудить решение о будущем взаимодействии с контрагентом / ми.

### 4. MCP — дополнительный канал

Рассматривается прототип read-only MCP с минимальными инструментами:

Он работает в двух режимах

1) В контуре решения в рамках платформы Альфа-Бизнес. Для обращения к информации в отчетах и выполнения работы агент будет использовать mcp, это часть решения - отдельный сервис.
2) Альтернативная ценность для клиента. Подключение инициирует клиент. Потенциально этот mcp-сервер можно будет использовать ai-native клиентам для организации работы с привычным ИМ агентом, для этого будет режим, который учитывает требования кибербезпасности банка, юридические и регуляторные риски. (см. кейсы mcp вкусвилл, tutu)

## Предварительные результаты

1. Уточнено место продукта в клиентском пути: после формирования списка потенциальных контрагентов (Альфа-Таргет) и до принятия обязательств по сделке.
2. Определено, что доступ по ИНН, сравнение и AI‑чат сами по себе не являются достаточным конкурентным преимуществом.
3. Сформулирована банковская ценность: актуальный структурированный dossier, единая семантика полей, evidence, дата среза и контролируемый доступ в UI и через MCP.
4. Подтверждено, что универсального списка главных сигналов нет; значимость зависит от цели проверки (для удобства пользователя представлена концепция ведения проектов по сделкам с контрагентами).
5. Выбрано разделение интерфейса на три уровня:
   - детерминированный отчёт и сравнение — не агент;
   - диалог поверх выбранного evidence — AI‑помощник;
   - проект с планом, инструментами, документами и памятью — агент.
6. Определён механизм потенциального влияния на retention (гипотеза):
   - повторное использование сервиса при следующей проверке;
   - рост воспринимаемой ценности Альфа‑Про;
   - возможное укрепление роли Альфы как основного операционного банка.

Последний пункт является гипотезой причинной связи. На текущем этапе нет данных, позволяющих заявлять о доказанном росте retention.


## План работ до финальной версии

### Этап 1. Детерминированный MVP

- реализовать адаптер выданного JSON;
- выбрать пять компаний для воспроизводимого demo fixture;
- собрать dossier и сравнительную таблицу;
- реализовать фильтры, shortlist и режим «только различия»;
- добавить evidence drawer и корректные состояния отсутствующих данных.

### Этап 2. Интерактивный AI

- реализовать передачу выбранного evidence в чат;
- ограничить ответы доступным контекстом;
- добавить обратные ссылки из ответа к данным;
- проверить отсутствие выдуманных чисел и неверной трактовки missing data;
- реализовать безопасный fallback без LLM.

### Этап 3. Минимальная агентная вертикаль

- создать сохраняемый проект проверки;
- показать цель и план углублённой проверки;
- реализовать 2–3 read-only обращения к dossier;
- загрузить один пользовательский документ;
- связать документ с открытым вопросом;
- показать diff и подтверждаемое пользователем обновление decision memo.

### Этап 4. MCP и внешний клиент

- реализовать минимальный read-only MCP либо его воспроизводимый прототип;
- добавить mock consent и scopes;
- показать разрешённый запрос и безопасный отказ;
- при наличии времени подключить Open WebUI или другой внешний AI‑клиент.

### Этап 5. Проверка и финализация

- провести benchmark «несколько PDF против workspace» на доступных тестировщиках;
- проверить все числа на golden fixture;
- провести red-team тесты на галлюцинации и ложную уверенность;
- проверить основной сценарий без сети/LLM;
- привести интерфейс к Alfa Core Components;
- подготовить демонстрацию продолжительностью до пяти минут;
- актуализировать описание проекта по фактически реализованным компонентам.
